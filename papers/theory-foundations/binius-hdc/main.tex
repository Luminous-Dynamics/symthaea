\begin{abstract}
Hyperdimensional Computing (HDC) uses high-dimensional binary vectors and operations such as XOR binding, majority bundling, and permutation. In characteristic-two arithmetic, XOR is addition and therefore does not require nonlinear AND/MUL gates. This paper reports a Binius64 constraint-integrity circuit for a 16,384-bit XOR relation and a public harness that generates and verifies the resulting proof. The reported constraint total also includes equality-wiring overhead.

The public artifact does not implement a Winterfell XOR prover in its benchmark harness: its Winterfell comparison is an analytic estimate. Accordingly, the same-scale cross-backend speedup and constraint-reduction ratios previously reported are retracted pending a reproducible, measured baseline. More importantly, the vendored `vendor/binius64/ARCHITECTURE.md` explicitly marks the standard Binius64 prover/verifier as **not zero-knowledge** and lists Iron Spartan as a separate zero-knowledge system. This harness depends on `binius-prover` and `binius-verifier`, not Iron Spartan, so witness-input privacy is not claimed. This is a proof-of-computation-integrity demonstration, not a privacy-preserving HDC implementation. Hamming-distance and multi-input-majority circuits are corrected; historical measurements are superseded pending test execution and fresh benchmarks. The temporal demo proves a packed-bit recurrence with witness-supplied gates, not numerical fixed-point CfC dynamics. Health-attestation and federated-learning end-to-end claims remain unsupported by this public artifact.
\end{abstract}

\noindent\textbf{Keywords:} computational integrity, hyperdimensional computing, binary fields, Binius64, proof circuits, CfC networks

\section{Introduction}
% ============================================================================

Hyperdimensional Computing (HDC)~\cite{kanerva2009hyperdimensional} encodes information as high-dimensional binary vectors (typically $D = 10{,}000$--$16{,}384$ bits) and performs reasoning through three algebraically simple operations: XOR binding ($\oplus$), majority-vote bundling, and cyclic permutation ($\rho$). These operations are computationally trivial---nanoseconds on commodity hardware---yet they enable robust classification, associative memory, and temporal sequence processing~\cite{rahimi2016robust}.

A useful goal is HDC computation with verifiable integrity. Privacy-preserving HDC is a stricter goal: it requires a zero-knowledge system or another separately justified confidentiality mechanism, not merely a circuit whose inputs are created as witness wires. The standard Binius64 prover/verifier backend used in this artifact is explicitly documented as non-zero-knowledge in the vendored architecture notes. Thus the experiments here address relation correctness and constraint cost only; privacy-preserving federated learning, anonymous eligibility, and selective credential disclosure are motivating research areas, not capabilities demonstrated by this harness.

\textbf{The Problem.} In a straightforward prime-field STARK arithmetization (e.g., using a system such as Winterfell~\cite{winterfell}), a designer may decompose $N$-bit values, constrain per-bit XOR ($c_i = a_i + b_i - 2a_ib_i$), and recompose the output, giving an illustrative $O(3N)$-constraint construction. For 16,384-bit HDC vectors this simple construction has about 49,152 bit-level constraints before considering alternative encodings or optimizer effects. This is an analytical construction sketch, not a measured Winterfell result; the public artifact leaves a semantically matched baseline open.

\textbf{Our Observation.} Binary tower fields $\mathrm{GF}(2^k)$ are constructed by successive quadratic extensions of $\mathrm{GF}(2)$. In these fields, addition \emph{is} XOR---it is the native field operation. The Binius proof system~\cite{diamond2023binius} operates over this exact algebraic structure. Therefore, HDC's XOR binding translates to field addition in Binius, requiring \textbf{zero non-linear (AND/MUL) constraints}.

\textbf{Contributions.}
\begin{enumerate}
    \item We identify the algebraic alignment between HDC operations and binary tower fields (Section~\ref{sec:alignment}).
    \item We implement and measure a Binius proof for a 16,384-bit HDC XOR relation. A same-scale comparison with a prime-field STARK is left open because the public harness's Winterfell values are analytic estimates, not measurements (Section~\ref{sec:evaluation}).
    \item We analyze a packed-bit recurrence circuit with witness-supplied gating words. This is not a numerical CfC proof; a fixed-point encoding and constrained numeric gating function remain future work (Section~\ref{sec:cfc}).
    \item We describe a proposed integration architecture for Mycelix. The public artifacts reviewed here do not independently establish a production deployment across 11 clusters (Section~\ref{sec:system}).
\end{enumerate}

\section{Background}
% ============================================================================

\subsection{Hyperdimensional Computing}

HDC represents concepts as binary vectors $\mathbf{v} \in \{0,1\}^D$ where $D$ is large (typically $10{,}000$--$65{,}536$). Three core operations form a complete algebra~\cite{plate1995holographic}:

\begin{itemize}
    \item \textbf{Binding} ($\oplus$): Element-wise XOR. Produces a vector dissimilar to both inputs. Used for role-filler associations.
    \item \textbf{Bundling} ($[\cdot]$): Element-wise majority vote. Produces a vector similar to all inputs. Used for set representation.
    \item \textbf{Permutation} ($\rho$): Cyclic bit rotation. Encodes sequential/temporal order.
\end{itemize}

Similarity is measured by normalized Hamming distance: $\delta(\mathbf{a}, \mathbf{b}) = \frac{1}{D}\sum_{i=1}^{D} a_i \oplus b_i$.

\subsection{STARK Proof Systems}

Scalable Transparent Arguments of Knowledge (STARKs)~\cite{ben2018scalable} prove computational integrity without trusted setup. A computation is encoded as an Algebraic Intermediate Representation (AIR)---a set of polynomial constraints over an execution trace. The prover commits to the trace via Merkle trees, and the verifier checks random evaluation points via FRI (Fast Reed-Solomon Interactive Oracle Proof).

The field over which the AIR is defined determines the cost of different operations. In a prime field $\mathbb{F}_p$, addition and multiplication are native, but bitwise operations require expensive decomposition. In $\mathrm{GF}(2^k)$, the situation is reversed: XOR (addition) is free, but arithmetic multiplication follows the tower field's irreducible polynomial structure.

\subsection{Binius: STARKs over Binary Tower Fields}

Binius~\cite{diamond2023binius} is a STARK system that operates over binary tower fields $\mathrm{GF}(2^k)$ constructed via the Wiedemann tower:
$$\mathrm{GF}(2) \subset \mathrm{GF}(2^2) \subset \mathrm{GF}(2^4) \subset \cdots \subset \mathrm{GF}(2^{128})$$

The key properties relevant to HDC:
\begin{itemize}
    \item \textbf{Addition is XOR}: $a + b = a \oplus b$ in $\mathrm{GF}(2^k)$. This is a \emph{linear} operation requiring zero non-linear constraints.
    \item \textbf{AND is the fundamental non-linear gate}: Bitwise AND maps to field multiplication in $\mathrm{GF}(2)$, costing 1 constraint per gate.
    \item \textbf{5$\times$ hardware efficiency}: Binary field operations achieve 1,909,854~Mmult/s/\textmu m$^2$ at 14nm, vs.\ 368,459 for Mersenne31~\cite{diamond2023binius}.
\end{itemize}

\subsection{Closed-form Continuous-time Networks}

CfC networks~\cite{hasani2022cfc} are temporal neural networks with closed-form solutions:
$$h(t) = (1 - \sigma(f(t))) \cdot h(0) + \sigma(f(t)) \cdot x_\infty$$
where $\sigma$ is sigmoid and $f(t) = -\Delta t / \tau$. Unlike ODE-based Liquid Time-Constant (LTC) networks that require iterative integration (e.g., RK4 with $S \approx 16$ substeps), CfC computes each timestep in $O(1)$ operations.

\section{HDC--Binius Algebraic Alignment}
\label{sec:alignment}
% ============================================================================

We now formalize the alignment between HDC operations and binary-field STARK constraints.

\begin{theorem}[Free Nonlinear XOR Cost]
Let $\mathbf{a}, \mathbf{b} \in \{0,1\}^D$ be binary hypervectors packed into 64-bit words. In the standard Binius64 circuit, computing each wordwise XOR introduces no nonlinear AND/MUL gate. The complete public-output relation still needs wordwise equality assertions to bind the claimed output $\mathbf{c}$ to $\mathbf{a} \oplus \mathbf{b}$; those statement checks must not be confused with zero total constraints or zero proving cost.
\end{theorem}

\begin{proof}
The Binius64 circuit operation $\operatorname{bxor}$ computes the packed-word XOR using a linear relation. The benchmark separately asserts equality between each XOR result and its public output word. These assertions bind the public statement, while the reported AND/MUL statistic measures nonlinear gates only. This algebraic accounting alone establishes neither total constraint count nor end-to-end proving performance. \qed
\end{proof}

\begin{corollary}[Bundling Cost]
The corrected generic circuit uses a bit-sliced binary counter followed by a per-lane threshold comparison. Its straightforward construction uses $O(D \cdot n \log n)$ bit-level gates; optimized constraint counts and timings must be measured from the corrected circuit rather than inferred from the former pairwise-AND implementation.
\end{corollary}

\begin{corollary}[Permutation Cost]
A permutation that only reorders whole packed words can be represented as an index reordering in the circuit. A general HDC cyclic bit permutation that shifts bits within or across packed words requires shift/rotation logic; this artifact does not implement or measure a general permutation circuit, so no zero-constraint claim is made for it.
\end{corollary}

\section{Packed-bit Temporal Recurrence Demonstration}
\label{sec:cfc}

The public temporal benchmark uses packed 64-bit words and bitwise XOR/AND gates, with a witness-supplied gating word. It does not encode the numerical CfC equation over fixed-point or floating-point values.

The numerical CfC update contains ordinary numeric subtraction, multiplication, and a sigmoid-like gating term. Those operations are not interchangeable with bitwise XOR and AND. The prior one-AND-per-neuron-per-timestep count applies only to the packed-bit relation, not to numerical CfC. The prior comparison to LTC+RK4 and the claim of a $16\times$ proof advantage are therefore withdrawn until equivalent numerical circuits, constrained gate computations, and reference-based correctness tests are implemented.

\section{What Is Free, What Is Not}
\label{sec:costs}
% ============================================================================

To prevent overreading the ``zero-cost XOR'' claim, we explicitly enumerate the cost structure:

\begin{itemize}
    \item \textbf{Free} (zero non-linear constraints): word-level XOR/addition. A permutation that only reorders whole packed words can be a reindexing; arbitrary bit-level cyclic rotation within/across packed words requires rotation/shift logic and must be costed separately.
    \item \textbf{Cheap} (1 AND per operation): Bitwise AND, comparison gates, threshold checks.
    \item \textbf{Statement wiring}: public-output equality checks remain part of the relation. Report total circuit structure separately from nonlinear AND/MUL counts; the current XOR benchmark reports the latter, and no fresh total-constraint count is claimed here.
    \item \textbf{Witness assumptions}: temporal demos use witness-supplied packed-bit gates. They do not constrain or verify a numerical sigmoid or prove the numerical CfC update.
    \item \textbf{Bundling evidence}: the former generic $n>3$ circuit implemented AND reduction, not majority. The correction branch uses a bit-sliced counter; all prior n>3 measurements are superseded until rerun.
\end{itemize}

\subsection{Claim Hierarchy}

We distinguish four levels of evidence strength:

\begin{enumerate}
    \item \textbf{Provable algebraic result}: XOR binding is linear in binary-field STARK AIR and incurs zero non-linear constraints. This follows from the definition of $\mathrm{GF}(2^k)$ addition.
    \item \textbf{Measured implementation result}: the public harness is designed to generate and verify a Binius proof for a 16,384-bit packed-word XOR relation. Fresh runtime, proof-size, and constraint measurements must be recorded from the corrected branch before publication; the current AND/MUL statistic is a nonlinear-gate count, not a count of equality wiring.
    \item \textbf{Cross-backend comparison}: not established by the public harness. Its Winterfell figures are analytic estimates; no same-scale Winterfell XOR proof is executed by the public benchmark.
    \item \textbf{Forward-looking implication}: binary-field proof systems are a promising fit for XOR-dominant workloads. The triple-stack and application-level conclusions remain speculative until their complete semantics and deployment paths are independently validated.
\end{enumerate}

\section{Related Work}
% ============================================================================

\textbf{ZKP for ML.} zkML~\cite{zkml2024} compiles ML inference to ZKPs with 3$\times$ proof compression. zkRNN~\cite{zkrnn2026} proves RNN execution but does not exploit closed-form solutions. SUMMER~\cite{summer2025} adds recursive ZKPs for RNN training. None address HDC-specific algebraic structure.

\textbf{HDC + Privacy.} EP-HDC~\cite{ephdc2025} achieves 36--1068$\times$ throughput improvement for HDC under BFV homomorphic encryption. PP-HDC~\cite{pphdc2024} provides a privacy-preserving HDC inference framework. Neither considers ZKP integration.

\textbf{Binary-Field Proofs.} Binius~\cite{diamond2023binius} develops proof systems over binary tower fields. Binius64~\cite{binius64} provides a Rust implementation with separate accounting for AND/MUL constraints. Our contribution is to demonstrate the algebraic alignment with HDC XOR binding in a public circuit harness; no general hardware-efficiency ratio is claimed from this experiment.

\textbf{Verifiable FHE.} vFHE~\cite{vfhe2023} adds ZKP verification to FHE with 15--20\% overhead. Combined with our HDC-Binius alignment, a ``triple stack'' (HDC + FHE + ZKP) becomes feasible where all three layers operate efficiently over binary fields.

\section{Discussion}
% ============================================================================

\textbf{The Triple Stack (Speculative).} HDC operations are simultaneously cheap under (1) FHE (XOR-only, no multiplications), (2) Binius STARKs (XOR = free), and (3) plaintext (nanoseconds). This alignment in $\mathrm{GF}(2)$ is suggestive but unverified---a prototype combining all three layers is needed before claiming a practical triple stack.

\textbf{Comparison with zkML.} Existing zkML systems optimize for general ML workloads: zkTorch reports 3$\times$ proof compression~\cite{zkml2024}, and zkLLM is cited for LLM inference performance~\cite{zkllm}. Our intended contribution is complementary: HDC XOR maps naturally to addition in characteristic-two fields. This algebraic observation does not by itself establish a practical speedup or a quantified constraint reduction. A fair comparison requires semantically matched circuits, published source and parameters, independently reproduced measurements, and equivalent security settings. General arithmetic ML circuits may not benefit comparably.

\section{Limitations and Threats to Validity}
% ============================================================================

\begin{enumerate}
    \item \textbf{Witness privacy is backend-specific.} The public HDC benchmark uses the standard Binius64 backend, which the vendored architecture document marks as non-zero-knowledge. The separate Iron Spartan smoke test does not migrate the full HDC relations or establish production-grade privacy. No HDC witness-confidentiality claim is made.

    \item \textbf{No measured cross-backend baseline.} The public harness does not implement or run a same-scale Winterfell XOR proof. Its Winterfell figures are analytical estimates and must not be used as measured proof times, proof sizes, or speedup ratios.

    \item \textbf{Relation scope.} Hamming distance is defined by constrained population counts of XOR words, and bundling by strict per-bit majority; the correction branch includes regression tests, but those tests and their performance measurements must pass/rerun before publication. The temporal demo is a packed-bit recurrence, not numerical CfC or sigmoid execution.

    \item \textbf{Application claims are not reproduced.} The current public path does not establish a deployed health-attestation pipeline, age credential, one-time-pad encryption correctness, encrypted numeric-gradient aggregation, or production Holochain deployment.

    \item \textbf{Historical performance data.} Previously reported local timings and proof sizes are historical reference values, not fresh measurements from the correction branch. No performance conclusion should be drawn from them until the current reproduction script completes and exact output is archived.

    \item \textbf{Experimental dependency.} The vendored proof-system code is evolving cryptographic software. Passing integration tests alone is not a security audit or deployment qualification.
\end{enumerate}
