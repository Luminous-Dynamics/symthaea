## Transfer-selectivity analysis

The analyzer consumes already-adjudicated outcomes; it does not adjudicate mathematical truth. Each input file must contain **only one selected split**. Example, after the isolated crate has been validated:

```bash
cargo run --locked --bin analyze_transfer_selectivity -- \
  data/benchmarks/proof-insight-transfer-v0/test-transfer-selectivity.jsonl \
  test \
  transfer-selectivity-report.json \
  10000 \
  20261021
```

Use `external_challenge` for a separately maintained external set. Do not mix train, validation, test, and external-challenge rows in one analysis input. The report hashes the exact input bytes, fixes the bootstrap seed and replicate count, resamples declared family-connected components, and emits 95% percentile intervals for compatible recall, incompatible false-accept rate, compatible false-reject rate, class-specific abstention rates, binary coverage, and selective risk.

`prediction.compatibility_probability` is distinct from action confidence: it means the estimated probability that the proposed transfer is compatible, regardless of whether the action is accept, reject, or abstain. The analyzer reports its scored coverage, Brier score, and ten equal-width reliability bins without imputing missing values. Probability metrics are descriptive until the rubric, calibration coverage, sample size, and independent cluster-level uncertainty are reviewed; missing calibration values do not count as a model failure or a success.

The analyzer deliberately emits `overall_confirmatory_decision = not_evaluated_...`: pair metrics alone cannot satisfy the preregistered finite mutation-suite gate or the primary exact-target proof-utility gate. The pair-track thresholds are diagnostics, not an overall SOTA or mathematical-correctness verdict.


## Counterfactual sensitivity analysis

The Rust `analyze_counterfactual_sensitivity` binary joins the suite's stable base/variant outcome IDs to the transfer-selectivity JSONL rows. The suite pins the source-artifact digest, then binds each outcome to a separate target artifact path and digest (base and counterfactual) plus the exact statement digest; two byte-distinct artifacts cannot claim one shared path or hash. The synthetic pair paths are placeholders and are not presented as real Lean files. For example, after both files have been checked against their JSON Schemas:

```bash
cargo run --locked --bin analyze_counterfactual_sensitivity -- \
  counterfactual-suite.json counterfactual-outcomes.jsonl test \
  counterfactual-sensitivity-report.json 10000 20261022
```

It checks source artifact/insight provenance, separate base/counterfactual target-artifact paths and digests plus statement digests, component IDs, labels/statuses, independent reviewer identities/evidence/reason codes, matched model/config/prompt/budget, the budget caps, and outcome-row uniqueness. Split/component isolation is checked across the whole suite, even when a run scores only one partition. The report separates compatible-base recall, counterfactual compatibility recall, sensitivity and false acceptance on incompatible variants, paired contract adherence, decision stability on semantics-preserving pairs, probability Brier score and mean no-op probability shift. It reports per-mutation-kind sensitivity / false acceptance, component-bootstrap intervals, and measured model-call/token/wall-time/cost totals and per-pair means for both sides, plus ratios and signed paired deltas. Costs use micro-USD. These paired target costs are diagnostic; estimating a full success-cost frontier requires multiple preregistered budget caps and outcome rows per method.

The report calls rates `ratio` and Brier / probability-delta metrics `mean`; it includes hashes of exact suite and outcome bytes. It always emits an unassessed confirmatory decision. This is intentional: a well-formed synthetic join does not establish expert-adjudicated compatibility, checker-backed transfer utility, or a SOTA result. CI uses the seven-pair, fourteen-row synthetic fixture to exercise the end-to-end path and mutates missing-row, provenance, reviewer-evidence and over-budget cases. The primary exact-target proof-utility endpoint remains unchanged.

## Required discipline

1. Pin the upstream repository commit and each source file digest. A branch name like `main` is not a reproducible source identity.
2. Distinguish headline theorem, formalized supporting result, informal manuscript claim, and reasoning summary.
3. Cite a specific source path and locator for each strategy claim. Keep excerpts short; prefer locators and authored paraphrases.
4. A strategy record must state preconditions and at least one failure boundary or explicitly state that the boundary is unknown.
5. Keep candidate transfer separate from verified transfer. A transfer is verified only when the exact target statement is checked by the declared proof checker under a recorded axiom/dependency policy.
6. Use the indexer's fixed family split; never reshuffle after inspecting difficulty or results. Keep companion results or alternate proofs in their original family. Audit cross-family dependencies and pretraining exposure separately; a family split is necessary but not sufficient.
7. Add semantic statement checks: confirm the formal statement faithfully encodes the intended claim, then use dependent-successor tests where meaningful downstream declarations exist. Include mutation controls so tests are shown to detect deliberately incorrect target variants.
8. Separate theorem proving from constructive problem-solving: on the latter track, the answer/witness must be discovered and all associated conclusions discharged. Track typechecked witness, proved obligations, and answer equivalence separately; compiling a plausible candidate does not count as solved.
9. Keep failed, timed-out, out-of-scope, and not-attempted states distinct. No silent drops.
10. No HDC/embedding field is authoritative for truth. Vector indexes, if added, are derived cache data and must be ablatable.
11. The frozen split manifest was generated from the pinned catalog with an independent implementation of SHA-256 ranking. It has not yet been matched against a compiled Rust indexer output; run the crate and `--verify-splits` before relying on it as an engineering-verified artifact.
12. Follow `evaluation-protocol.md`: select settings and the strongest baseline among A–E and I on validation families only, freeze the primary contrast and compute budget before the test run, preserve all exclusions, and report paired family-level outcomes with uncertainty. Do not make SOTA claims from this pre-screen split alone.
13. Run the analyzer's `--mode power` using raw validation JSONL before held-out scoring. It recomputes baseline scores and eligible-family sizes, then simulates the primary gate over 0/+10/+15/+20pp effects and ICC 0/0.05/0.10/0.20. Require the registered +20pp/ICC 0.20 power and zero-effect false-claim gates; otherwise expand the external set or label the study a pilot.
14. After `--mode power` emits a passing report, hash the report and add its digest as `power_report_sha256` to the final frozen run config. Then pass that same file using `--power-report` to analyze mode; the analyzer independently reruns the validation-only scenarios before it will score test rows. See the [executable analysis contract](analysis-contract.md) for the exact two-stage commands and no-go behavior.

## No claims yet

Creating this schema or protocol does not establish that the records are complete, that the schema has been validated by an independent JSON Schema implementation, that proof insights transfer, or that Symthaea outperforms any baseline. Those require the stated validation gates and actual measured experiments; see also [the research design](../../../docs/research/proof-insight-transfer-2026.md).

15. After the protocol amendment, every future frozen run config must hash the current protocol bytes. The secondary transfer-selectivity outcome schema separates gold labels from model decisions; keep unresolved reviewer disagreements as `unknown`, report compatible-positive recall as well as incompatible false-accepts, and never interpret a structurally valid JSON row as a verified mathematical judgment.

16. For transfer selectivity, score only the preselected split using `analyze_transfer_selectivity`; report raw denominators, component counts, abstention, false acceptance, compatible recall, Brier score/reliability when available, and cluster-bootstrap intervals. The analyzer's overall decision is intentionally fail-closed pending an independent negative-control receipt and the primary proof-utility gate.


## Multi-budget success–cost frontier analysis

After creating and reviewing a real, frozen plan and executing its full assignment matrix, analyze the target × arm × budget ledger with:

```bash
cargo run --locked --bin analyze_success_cost_frontier -- \
  success-cost-frontier-plan.json outcome-ledger.jsonl \
  frontier-report.json 10000 20261023
```

Each outcome must match the plan's run ID, target, component, arm, budget, and input digest. Executed rows must include receipts for the exact target statement, kernel/checker, semantic gate, successor gate, and run; resource use must stay within the assigned caps. Missing runs are not silently dropped. The primary success curve uses the full assigned target denominator, so unattempted/unavailable cases remain non-solves. Report the paired component-clustered interval for each same-budget arm contrast, actual cost per assigned target, cost per verified solve where defined, and the observed non-dominated success/cost points. Do not interpolate between unmeasured caps.

The frontier analyzer is deliberately **descriptive only**: `confirmatory_decision` is permanently `not_evaluated_*`; it does not open checker receipt contents, independently certify statement correspondence, or replace `analyze_pitb_results` and its pre-registered power/primary-utility gate. A successful JSON/Rust pipeline would qualify the analysis harness, not establish insight-transfer utility or a state-of-the-art win.


## Cross-family leakage audit

- **family-leakage-edges.schema.json** and **family-leakage-report.schema.json** define a secondary, non-destructive audit for cross-family dependencies. The Rust analyzer recomputes the frozen assignment, binds the edge inventory to its partition digest, joins confirmed and unresolved hard-leakage edges into connected components, and reports conservative quarantine counts.
- **fixtures/family-leakage-edges.synthetic.json** contains deliberately invented negative/control relationships for CI only. It is not an actual dependency inventory and must not be treated as evidence about those families.
- The real relationship inventory has not yet been independently curated. Its status is incomplete; therefore, the system cannot certify the frozen test split as leakage-free. The audit preserves the original split and does not turn metadata checks into mathematical evidence.

### Title-only candidate discovery

`discover_family_leakage_candidates` is a deterministic first-pass triage tool. It reads only the frozen family titles, normalizes away markup, downweights common tokens using document frequency, and emits candidates with shared-token explanations, a Jaccard score, a rarity score and an evidence digest. It is run twice in CI and the exact outputs must match.

The output schema is `family-leakage-candidate-discovery.schema.json`. Candidate rows are always marked `title_similarity_only` and `unreviewed`. They are not converted automatically into hard leakage edges, do not change the split, and must not be counted as dependency or contamination findings. This screen is intended to prioritize expert review; it can both miss real dependencies and surface unrelated theorems with overlapping words.
### Separate artifact-path candidate channel

`discover_artifact_path_candidates` scans the manifest's linked artifact paths independently of title similarity. It strips generic directory, filename, publication-date and document-type tokens, computes rare path-token overlap, and emits the actual matching paths alongside shared-token explanations and a content digest. Its output schema is `family-artifact-path-candidate-discovery.schema.json`.

Every row is forced to `artifact_path_similarity_only` and `unreviewed`. Path slugs are metadata, not artifact bytes: overlap does not prove that two families share a source document or a mathematical dependency. The path channel has its own thresholds, output and reproducibility check; do not combine its scores with the title channel without a preregistered calibration.

## Simulation-based power planning

`crates/bridges/symthaea-proof-insights/src/bin/plan_pitb_power.rs` is a deterministic planning simulator for the registered paired, family-clustered exact-target success gate. It accepts the observed or proposed component-size vector instead of treating all theorem families as equally sized, models shared family difficulty with a beta-binomial sensitivity parameter, and reports estimated probability of meeting the preregistered gate:

- observed treatment-minus-control success-rate difference is at least the selected minimum gain (the current research target is +10 percentage points);
- the approximate 95% cluster-level interval has a lower bound above zero;
- degenerate zero-width intervals never count as passing.

Example (synthetic planning assumptions only; 20 cluster sizes shown):

```sh
cargo run --locked --bin plan_pitb_power -- \
  0.35 0.15 0.10 0.05 0.05 0.5 \
  2,3,1,4,2,2,3,1,4,2,3,1,2,4,1,3,2,2,4,1 \
  10000 1000 12345 power-plan.json
```

The output is governed by `power-planning-report.schema.json`. The parameters after ICC are the standard deviation of a family-level treatment-effect deviation on the probability scale and a pair-association fraction: 0 means independent potential outcomes conditional on family success probabilities, while 1 reaches the Frechet upper bound on joint success. This association fraction is not a Pearson correlation. The treatment effect can vary by family and can be negative; success probabilities are clipped to [0,1], so the report exposes the generated marginal gain rather than assuming it equals the input.

Repeat across a predeclared sensitivity grid over baseline success, expected gain, ICC, family-effect heterogeneity, and pair association; use the real eligible connected-component sizes once the relationship audit is complete. The component-percentile interval uses the supplied number of bootstrap replicates (minimum 1,000) and resamples whole components; it follows the paired-delta interval procedure used by PITB's success-cost frontier analyzer. The model is a planning sensitivity analysis, not an estimate of PITB's effect distribution or pair correlation. Do not use synthetic assumptions to claim that the benchmark is powered, and do not tune assumptions after observing held-out outcomes.


### Exploratory power sensitivity

See [the 24 October sensitivity illustration](../../../docs/research/pitb-power-planning-sensitivity-illustration-2026-10-24.md). It uses a separate exploratory Monte Carlo implementation—not the Rust binary or CI—to show that the 20-component floor is not a power guarantee. Under one synthetic setup, the configured +15-point gain reached roughly 80% gate power only around 50 independent components. This is conditional planning evidence only; it is not a target sample size for the real benchmark. Recompute after the audited eligible-component distribution is frozen, using a preregistered sensitivity grid and independent statistical review.


The planner's decision gate now uses a paired, component-percentile-bootstrap interval rather than the earlier t-interval approximation. Its bootstrap replicate count is an explicit CLI parameter, is recorded in the report, and is checked by the report schema. This aligns the interval method with the benchmark's paired frontier analysis; the planning model remains approximate because the generative assumptions are unestimated and the finite number of bootstrap replicates adds Monte Carlo variability.
