# QUAL-INFRA-003A — Hermetic Qualification Policy

Status: source policy only. No namespace executor, qualification result, runtime authority, hardware observation, or physical-safety claim is established by this document.

## Objective

QUAL-INFRA-003 strengthens the provenance-preserving unprivileged execution model from QUAL-INFRA-002 into a namespace-contained execution environment for future exact-subject qualification.

The subject process should see only the exact read-only source, exact read-only toolchain, exact read-only materialized dependencies, a pinned read-only runtime root, and explicitly declared writable working state. The trusted control plane and evidence output must not be visible from inside the subject namespace.

## Backend decision

The primary v2 backend is Bubblewrap on the GitHub-hosted Ubuntu 24.04 VM runner.

The reviewed Ubuntu 24.04 package version is `bubblewrap 0.9.0-1ubuntu0.3`. Actual package/binary identity must be re-established and bound into execution evidence; this policy does not claim that Bubblewrap is already installed.

Setuid Bubblewrap is not admitted. The backend must use unprivileged user namespaces with `no_new_privs` and no active Linux capabilities.

Ubuntu 24.04 can restrict unprivileged user namespaces through AppArmor. v2 prefers narrowly scoped Bubblewrap permission such as `bwrap-userns-restrict` when available and fails closed when the required profile cannot be established. Globally disabling `kernel.apparmor_restrict_unprivileged_userns` is not admitted.

## Two-phase model

### Phase A — trusted materialization

Only trusted control-plane code may perform materialization. Subject-owned build scripts and tests do not execute here.

Materialization may use the network and must produce immutable, digest-bound outputs for:

- runtime root filesystem;
- Rust toolchain;
- a Cargo-vendored dependency tree;
- a trusted Cargo source-replacement configuration;
- a materialization manifest describing every input identity and digest.

The Cargo configuration must point dependency resolution at the read-only vendored tree. An unpinned floating image tag or network-fetched dependency is not a valid Phase-B input.

### Phase B — offline qualification

Subject qualification runs with network policy `NONE`, Cargo offline mode, and only the frozen outputs of Phase A plus the exact source subject.

Cargo's **dependency content** stays under read-only `/deps`. Cargo's own mutable bookkeeping/cache/lock state belongs under private writable `/work/cargo-home`. This prevents a build script from mutating the dependency evidence while still allowing Cargo to create legitimate local lock/cache metadata.

Every trusted Cargo command uses the frozen `/deps/cargo-config.toml` and offline mode explicitly. No dependency resolution or retrieval may silently occur during Phase B.

## Namespace model

The pinned runtime rootfs is mounted read-only at sandbox `/`, so dynamic loader/library/runtime resolution comes from the frozen runtime substrate rather than the GitHub host.

The execution namespace then layers:

| Path | Policy |
| --- | --- |
| `/` | pinned runtime rootfs, read-only |
| `/src` | exact source subject, read-only |
| `/toolchain` | exact pinned Rust toolchain, read-only |
| `/deps` | exact Cargo vendor tree + trusted Cargo config, read-only |
| `/work` | private writable build/Cargo state |
| `/home` | private writable home |
| `/tmp` | private writable temporary storage |
| `/proc` | explicitly created private proc filesystem |
| `/dev` | minimal explicit device set |

The trusted control-plane checkout, qualification evidence directory, host `/tmp`, and unrelated runner workspace paths must not be mounted into the namespace.

All mount arguments are generated by trusted control-plane code from a closed profile. The qualification subject cannot supply arbitrary mount paths or Bubblewrap arguments.

## Environment

The closed qualification environment requires at minimum:

- `LANG=C.UTF-8` and `LC_ALL=C.UTF-8`;
- `TZ=UTC`;
- `HOME=/home`;
- `TMPDIR=/tmp`;
- `CARGO_HOME=/work/cargo-home`;
- `CARGO_TARGET_DIR=/work/target`;
- `PATH=/toolchain/bin:/usr/bin:/bin`;
- Cargo network offline mode;
- no inherited global/system Git configuration;
- no GitHub token, cloud credential, SSH agent, signing agent, Docker socket, or host package-manager credential.

The runtime rootfs must contain every non-toolchain executable/library intentionally admitted by the closed profile. Falling back to host `/usr`, `/lib`, `/etc`, or other host runtime paths is outside v2 semantics.

## Stable versus execution-specific identity

The future compiler/executor must distinguish:

- a **semantic qualification-plan identity**, derived from schemas, commands, guest mount semantics, environment and cryptographic input identities; from
- an **execution-instance identity**, which may additionally bind ephemeral host materialization paths used by one runner invocation.

Ephemeral runner paths such as `/home/runner/work/...` must not redefine the semantic qualification proposition by themselves.

## Namespace and privilege requirements

The subject environment must unshare user, IPC, PID, UTS, cgroup, and network namespaces; start a new session; die with the sandbox parent; run with `no_new_privs`; and expose no active Linux capabilities.

Nested namespace creation from inside the subject sandbox is not part of v2 authority and must fail in adversarial qualification.

## Adversarial qualification gates

A v2 executor is not eligible for use until executable tests demonstrate all of the following:

1. writes to `/src` fail;
2. writes to `/toolchain` fail;
3. writes to `/deps` fail;
4. writes to the runtime root fail;
5. control-plane bytes cannot be read;
6. evidence bytes cannot be read or written;
7. host `/tmp` and unrelated host workspace paths cannot be reached;
8. source symlinks cannot escape the source mount;
9. subject input cannot add arbitrary mounts or Bubblewrap options;
10. outbound network connections fail;
11. DNS resolution requiring external network access fails;
12. nested namespace creation fails under the selected policy;
13. privilege escalation attempts fail;
14. residual child processes die with the namespace;
15. exact source identity is unchanged after execution;
16. exact toolchain identity is unchanged after execution;
17. exact dependency identity is unchanged after execution;
18. exact runtime-root identity is unchanged after execution.

A test being specified here is not evidence that it has passed.

## Evidence requirements

A future v2 receipt must bind at least:

- exact control-plane commit/tree;
- exact executor/policy/profile bytes;
- semantic plan digest and execution-instance digest;
- Bubblewrap package version and binary SHA-256;
- user-namespace/AppArmor setup evidence;
- runtime-root identity and digest;
- Rust toolchain identity and digest;
- Cargo vendor/config materialization manifest and digest;
- exact source commit/tree and immutable digests;
- exact closed argv and environment;
- namespace/mount/network policy actually used;
- adversarial-gate results;
- command logs/digests;
- source/toolchain/dependency/runtime postflight identities;
- complete evidence-payload checksums;
- uploaded artifact identity/digest.

## Migration rule

QUAL-INFRA-003 is a new evidence lineage. It must not rewrite, upgrade, or reinterpret a QUAL-INFRA-002 receipt. Downstream promotion logic that wants hermetic-v2 evidence must bind v2 explicitly.
