# SYM-FIN-SYS-016 — Provenance Gap Register and Assurance Plan

**Status:** research design note  
**Claim ceiling:** synthetic/deterministic research only  
**As of:** 2026-10-16  
**Scope:** the run-receipt contract and artifact manifest in this PR

## Executive finding

The v1 artifact manifest is a useful **integrity contract**, but integrity is not authenticity, authenticity is not evidence that a run actually happened, and an authentic run receipt is not proof that its economic claims are true.

The current validator checks exact-byte SHA-256 digests for eight repository artifacts, binds each SHA-256-shaped receipt field to one manifest entry, validates the manifest's own digest, and explicitly marks 18 of the 19 illustrative receipt digest values as unavailable/unverified. That is honest and valuable. It does not yet authenticate the manifest or receipt, prove a trusted workflow executed, or inspect the missing run-generated bytes.

One additional contract gap deserves closure: source artifact IDs and paths are pinned, but the declared role label is not currently compared with a pinned role catalogue. A digest can identify bytes without proving that the label attached to those bytes is semantically correct.

## Paradigm shift: assurance is a vector, not a green check

Do not reduce evidence quality to a single boolean "verified". Track distinct assurance dimensions and preserve unknown values:

| Dimension | Question answered | Current v1 boundary |
|---|---|---|
| Byte integrity | Do available bytes match the declared digest? | Checked for the eight pinned repository files and the exact manifest bytes. |
| Binding completeness | Does every digest-shaped receipt field have one matching manifest binding? | Checked structurally; 18 illustrative run-generated payloads remain unavailable/unverified. |
| Source authenticity | Is the statement attributable to an authorized issuer or builder? | Not established by a plain hash manifest. |
| Execution authenticity | Did the claimed workflow/run execute for the exact commit, workflow revision, and attempt? | Not established by fixture validation. |
| Semantic validity | Does the receipt satisfy the schema and the cross-field contract? | Validator and tests are authored; exact-head execution remains unqualified until a run proves it. |
| Domain validity | Do the results describe the world, and support the causal claim being made? | Outside this synthetic-only contract. |
| Authority | May this evidence trigger a consequential action? | None. The research receipt grants no production authority. |

A future receipt should report this vector explicitly. Missing source bytes must not become "verified" merely because a syntactically valid digest is present. Authentic metadata can still contain false claims; signatures answer who made a statement, not whether the statement is true.

## Provenance architecture to target

Use existing attestation standards instead of inventing a bespoke signing envelope. The [in-toto Attestation Framework](https://github.com/in-toto/attestation/blob/main/spec/README.md) separates a statement about a subject from its predicate and authentication envelope. [SLSA build provenance v1.2](https://slsa.dev/spec/v1.2/build-provenance) defines metadata about where, when, and how an artifact was produced. These standards can establish authenticated production metadata; they do not certify socioeconomic truth or fairness.

A staged design should add:

1. **Exact subject binding.** Record repository URI, full commit SHA, path or immutable artifact identity, byte digest, schema version, and the exact registry/manifest digest. A branch name alone is not an immutable subject.
2. **Authenticated execution statement.** Bind the receipt to a trusted builder identity, immutable workflow definition/revision, workflow run ID and attempt, toolchain/container identities, invocation parameters, and completion status. Verify the issuer against an explicit trust policy rather than trusting an arbitrary self-declared key.
3. **Payload availability and verification.** Every artifact declared verified must be fetchable by a verifier (or included in a documented content-addressed bundle), and its bytes must hash to the declared digest. An unavailable artifact remains unavailable; a digest placeholder is not evidence.
4. **Typed evidence and role policy.** Pin the allowed triples (artifact_id, path, role), not only IDs and paths. Distinguish source materials, executable/evaluator artifacts, run-generated inputs, outputs, and counterexamples.
5. **Bounded claims.** Bind every metric result and counterexample to the evaluator digest, policy/profile digest, input digest, seed, and run identity. Keep synthetic, simulated, observed, independently verified, and authorized as separate labels.
6. **Revocation without erasure.** Corrections, compromised issuers, superseded profiles, and failed attestations should append new status events referencing the prior record. Do not silently rewrite historical evidence.
7. **No authority escalation.** A valid attestation may upgrade provenance assurance only. It must never, by itself, authorize settlement, affect reputation, assign civic rights, or make a model output binding.

This design deliberately composes with federated domain adapters; it does not require a universal ledger or one global economic ontology. Mappings to systems such as [ValueFlows](https://www.valueflo.ws/specification/vfspec/) must preserve distinctions between planned commitments and observed economic events rather than promote a provider assertion into an observed fact.

## Qualification gates and falsifiable targets

All values below are **proposed acceptance criteria**, not measured results. Report the exact artifact commit and exact run identity with every future pass/fail result.

| Gate | Required experiment | Proposed acceptance target |
|---|---|---|
| Q0 — local integrity | Re-hash the eight pinned source files and exact manifest bytes; enumerate receipt digest pointers. | 100% digest matches; exactly one binding per digest pointer; zero unknown or duplicate pointers. |
| Q0 — semantic negative controls | Run all pinned schema and semantic mutations against the actual schema engine and validator. | 26/26 controls rejected, positive fixture accepted only under the declared synthetic-only claim ceiling; record all 11 authored tests on the exact head. |
| Q1 — role integrity | Mutate each declared role while keeping IDs, paths, and bytes fixed. | 100% of role mutations rejected; only pinned ID/path/role triples accepted. |
| Q1 — authenticated provenance | Verify signed statements against an allowlisted builder/issuer policy. Mutate subject, commit, workflow revision, issuer, signature, and run attempt. | 100% of valid accepted receipts authenticate the exact subject; 100% of invalid/tampered/unauthorized cases are rejected. |
| Q2 — payload evidence | Remove or alter each referenced run-generated payload, including inputs, event payloads, metrics, and counterexamples. | Zero unavailable or mismatching payloads represented as verified; 100% of required verified payloads are byte-available and digest-matched. |
| Q3 — replay | Repeat deterministic runs under a pinned environment with identical inputs and seeds. | 100/100 same-input replays yield identical ordered event and output digests. For deliberately stochastic runs, preregister statistical tolerances instead of claiming bitwise determinism. |
| Q4 — socioeconomic validity | Preregister hypotheses, regimes, metrics, seed schedule, exclusions, and negative controls before running mixed-regime and bridge scenarios. | Report effect sizes and uncertainty intervals, not only averages or a composite score; zero post-hoc deletion of failed/negative trials. |
| Q5 — safety under concurrency | Model and test duplicate delivery, concurrent reservations, retries, process restarts, partitions, stale attestations, and conflicting finality. | Zero safety invariant violations in the stated finite model and test corpus; publish state-space coverage and counterexamples. Do not extrapolate serial tests into a distributed-safety claim. |
| Q6 — anti-gaming and impact | Test Sybil identities, collusion, metric gaming, strategic under-reporting, and ecological or welfare externalities. | Publish false-positive/false-negative rates, performance by regime and affected subgroup, and explicit failure conditions. No single welfare or efficiency metric may erase severe harm on another axis. |

The existing proposed 12,000 regime/shock runs and 16,800 directed bridge runs can become useful only after scenario schedules, exclusions, primary metrics, and evaluation code are preregistered and digest-bound. Their workload size is not evidence of validity. Separate exploratory runs from confirmatory evaluation and disclose negative results.

## Failure modes this plan is meant to prevent

- Treating a correct hash as a signature or a signed statement as truth.
- Accepting a manifest whose role labels have drifted while its file hashes remain valid.
- Reporting a digest for absent payload bytes as if those bytes had been inspected.
- Replaying a fixture and describing it as a real experimental run.
- Reporting a completed/skipped/queued workflow as a test pass.
- Optimizing aggregate throughput or a composite wellbeing score while hiding concentration, coercion, ecological overshoot, unequal access, or worse outcomes for a subgroup.
- Letting a research receipt or model recommendation silently acquire financial or civic authority.

## Immediate next work

1. Add and test the pinned role catalogue, with one negative control per role mutation.
2. Extend the receipt with authenticated run identity and trusted-builder provenance in a separately versioned schema; do not break or silently reinterpret v1.
3. Add exact-head machine-readable qualification output that distinguishes not_run, queued, skipped, failed, and passed.
4. Keep the 18 illustrative unavailable payloads marked unverified until real payload bytes are supplied; do not make the current fixture a false production-positive.
5. Only after provenance and semantic gates are qualified, start confirmatory mechanism-design campaigns.

The intended result is not "a verified number." It is an independently checkable chain of bounded claims whose byte identity, issuer, execution, interpretation, and authority limits remain separately inspectable.
