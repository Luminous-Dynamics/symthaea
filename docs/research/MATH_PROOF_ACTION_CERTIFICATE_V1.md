## 1. Research objective

Make the mathematical explanation itself auditable. A final Lean kernel-accepted theorem establishes the exact formal statement under a pinned environment. It does not automatically establish that a generated proof plan correctly describes the proof's local warrants, consumed hypotheses, side conditions, subgoals or conceptual role.

The proposed system attaches a local proof certificate to every formalizable plan action and validates the composition of those actions. Interpretive and pedagogical claims remain separately classified and independently reviewable.

## 2. Evidence layers

Keep these authorities distinct:

1. **Final theorem authority:** Lean kernel acceptance for the exact root theorem type in a pinned environment.
2. **Local action authority:** Lean kernel acceptance for the exact proposition proved by an individual plan action.
3. **Plan-composition authority:** structural and proposition-identity checks that connect inputs, outputs, subgoals, assumptions and terminal claims.
4. **Mathematical-role authority:** independent expert review of the conceptual role represented by a formal action or dependency.
5. **Pedagogical authority:** human comprehension/transfer measurements for whether the explanation actually teaches the mechanism.

No layer silently inherits authority from another. A kernel-checked local lemma does not by itself prove that its natural-language role label is correct. An expert explanation is not a kernel proof.

## 3. ProofActionCertificateV1

A certificate for one formalizable action binds:

- source repository, commit, file/blob and fully qualified declaration;
- Lean/Mathlib toolchains, Lake manifest, import closure and checker version;
- pre-action goal type identity and canonical digest;
- universe parameters, binder identities/types, local context and local instances;
- exact consumed hypotheses and premise type identities;
- side-condition identities/types and the action obligations they support;
- output subgoal proposition identities/digests;
- local proof artifact reference and digest;
- exact expected proposition proved by the artifact;
- kernel replay result;
- axiom, admission and sorryAx dependency closure;
- coercions, reducible definitions, typeclass resolution and relevant elaboration evidence;
- reviewer disposition for any conceptual-role interpretation.

A local certificate cannot be created by matching a declaration name or a graph edge. The proof artifact must establish the exact local proposition generated by the recorded context.

## 4. Action trust states

Use explicit states:

| State | Meaning |
|---|---|
| kernel_checked | Exact local transition proof accepted by Lean under the pinned environment |
| formally_represented_not_replayed | Formal source/type evidence exists, but the local proof receipt has not been replayed |
| expert_reviewed_interpretation | A mathematical role/meaning has been reviewed, but is not itself a formal theorem |
| analogy_with_boundary | Pedagogical analogy with an explicit scope boundary |
| unknown | Evidence is missing, ambiguous or unsupported |

Unknown is a valid outcome. Do not convert missing proof artifacts into an empty dependency list or a passing status.

## 5. Compositional validation

For a ProofPlanV1 plan, check:

1. The root goal is identical to the pinned theorem target.
2. Each action's input goal identities equal the obligations produced by earlier actions.
3. Each consumed hypothesis/premise/side condition exists in the exact local context.
4. Each output subgoal is consumed later, kernel-discharged, or explicitly retained as unresolved.
5. Every terminal claim is the root theorem or a separately proved corollary.
6. No action changes binders, universes, domains, local instances or assumptions without an explicit transport.
7. Every local certificate replays under the same environment and declared axiom policy.
8. Every mathematical interpretation claim is separately reviewed; source dependency does not imply mathematical necessity.

Plans need not be DAGs. Preserve branching, merging, cycles at the conceptual level and multiple valid proof routes. Do not require tactic-trace or source-graph identity.

## 6. Initial bounded corpus

Start with:
- provisional And.comm ProofPlanV1 plan from the existing pilot;
- Nat.choose_pos;
- Set.countable_union;
- Multiset.map_id;
- Finset.card_map.

For each:
- pin source/toolchain/imports;
- extract the root theorem and relevant elaborated local goals;
- select a small number of action boundaries;
- build local certificates where a transition can be represented as an exact Lean declaration or generated theorem obligation;
- distinguish direct formal dependencies from the action's mathematical warrant;
- obtain two independent expert role annotations and adjudicate disagreement.

The And.comm proof plan is still provisional until its exact type/environment receipt and expert review exist.

## 7. Adversarial controls

- Replace a local proof artifact with one proving a similar but non-equivalent proposition.
- Alter one binder type, universe or local instance while retaining the surface theorem name.
- Remove a positivity, injectivity, nonempty or finiteness condition consumed by an action.
- Omit one generated subgoal from the plan graph.
- Mislabel an infrastructure dependency as the key mathematical argument.
- Supply a valid alternate proof route that differs from the source tactic trace.
- Use an opaque helper or unavailable proof value.
- Include an axiom/admission boundary.
- Change only the explanation text while leaving the Lean proof unchanged; reviewers must detect a role-description mismatch.

A failed local proof replay is a local certificate failure. It is not automatically a refutation of the root theorem.

## 8. Metrics and prospective gates

Report independently:
- local-action kernel replay rate;
- exact goal/hypothesis/context binding accuracy;
- side-condition-to-action coverage;
- subgoal accounting completeness;
- terminal root-goal coverage;
- axiom/admission disclosure;
- alternative-route acceptance;
- mathematical-role annotation agreement/precision;
- false local-action acceptance;
- unresolved rate;
- Lean elaboration time, checker cost and expert review minutes.

Prospective pilot targets:
- 100% exact local goal/context identity for actions marked kernel_checked;
- 100% replay of claimed local certificates;
- 100% axiom/admission disclosure;
- zero observed false local-action acceptance on seeded negative controls;
- at least 95% side-condition and subgoal-accounting coverage;
- at least 80% independent expert acceptance of the complete plan-to-proof mapping;
- no penalty for independently kernel-checked alternative routes to the same theorem.

These are targets, not current results.

## 9. Competitive positioning

The point is not to out-scale TheoremGraph/LeanGraph or out-prove FormalMATH leaders. Reuse the external graph/retrieval layer, then test whether exact local warrants and compositional certificates improve proof-plan fidelity, counterfactual diagnosis, explanation reliability and transfer.

ProofGrid contributes first-failure localization. ProofRank contributes proof-quality dimensions. QEDBench demonstrates the need for independent evaluation rather than relying on LLM judges. The local-certificate layer supplies a hard formal authority where the claim is formalizable, while expert review handles mathematical role and human study handles learning.

## 10. Execution order

1. Freeze the ProofActionCertificateV1 schema and trust-state semantics.
2. Build a small Lean tool to emit exact local goal/type/proof receipts from a pinned environment.
3. Certify a few And.comm actions.
4. Extend ProofPlanV1 validation to check certificate references and subgoal composition.
5. Add mutation fixtures and exact-head workflow checks.
6. Obtain two blinded role annotations.
7. Extend to the four Mathlib seed declarations.
8. Compare source graph only, ProofPlanV1, and ProofPlanV1 plus local certificates.

## 11. Claim ceiling

- Final theorem kernel acceptance does not certify the generated explanation.
- A local certificate proves its exact proposition, not the human interpretation of its role.
- A dependency occurrence does not prove mathematical necessity.
- Tactic traces are not the only valid proof plan.
- Expert-reviewed concepts are not kernel theorems.
- No ProofActionCertificateV1 implementation or measured outcome exists.


## 12. First source-pinned Lean pilot (2026-11-24)

A bounded pilot now exists for the three formal plan actions in the provisional `And.comm` fixture:

- Source: [ProofActionCertificateAndComm.lean](../../scripts/research/lean-proof-extractor/ProofActionCertificateAndComm.lean).
- Candidate mapping: [PROOF_ACTION_CERTIFICATE_AND_COMM_V1.json](PROOF_ACTION_CERTIFICATE_AND_COMM_V1.json), validated against [its schema](PROOF_ACTION_CERTIFICATE_AND_COMM_V1.schema.json).
- Environment: Lean `4.37.0-rc1`, Mathlib repository commit `6ebcce37335bcb6bca64596e5d57bb3035648030`, with Lean core revision `0b77e12952ad39077d80d8bd6b66d601f225c321`.
- `A_SPLIT_IFF`: a Lean theorem establishes that the parent iff proposition is equivalent to the conjunction of the forward and reverse implication obligations.
- `A_FORWARD` and `A_REVERSE`: explicit local theorems use `And.symm` to prove the exact directional propositions.
- `and_comm_plan_replay`: composes those two local certificates into the root iff theorem.

The focused workflow now replays this Lean source after verifying the source SHA-256, pinned Mathlib revision and toolchain. On success it generates a machine-readable receipt containing the Symthaea commit, Lean version, Mathlib revision, Lake manifest digest, proof-source and manifest digests, action declaration mapping, and the hash of the raw `#print axioms` log. The replay log and receipt are uploaded as a workflow artifact. The committed manifest deliberately remains `kernel_replay_pending`; only the generated exact-run receipt can record an accepted result.

**Current evidence boundary:** the source and workflow have been committed, but this turn did not run the Lean toolchain locally and no exact-head replay result is yet available. The pilot checks the declared local propositions and their composed root theorem; it does not yet emit elaborated pre/post goal-state snapshots, binder identity or local-instance context digests, parse the axiom/admission closure into structured fields, or validate arbitrary plan graphs. The action-to-plan mapping and mathematical-role descriptions remain provisional and unreviewed.

### 12.1. Wrong-proposition rejection control

A pinned negative Lean source, [ProofActionCertificateAndCommNegative.lean](../../scripts/research/lean-proof-extractor/ProofActionCertificateAndCommNegative.lean), attempts to reuse `And.symm` for an identity proposition (`a ∧ b → a ∧ b`) rather than the declared swap proposition. The manifest pins this file's SHA-256 and requires the expected result `lean_type_error`.

The focused workflow must: (a) run the positive local-action source successfully; (b) run the negative source and require a Lean type/application-type mismatch diagnostic; and (c) fail the job if the negative source is accepted. The replay artifact records both the positive log digest and the expected negative rejection log digest. A generic process failure does not satisfy the negative-control check.

This is one seeded mismatch control only. It is not a comprehensive adversarial suite, and the negative-control result remains pending until an exact-head workflow run reports it.

### 12.2. Manifest-to-plan consistency gate

The focused workflow now cross-checks the certificate manifest against the source-pinned `PROOF_PLAN_AND_COMM_V1.json`: plan IDs, action node IDs, action kinds, input goal IDs and output subgoal IDs must match. The forward and reverse expected propositions must equal the corresponding plan subgoal statements. A generated mutation that changes the forward expected proposition to the identity statement is required to fail this structural binding check.

This is a finite manifest-to-plan integrity gate; it does not make the candidate plan expert-reviewed gold data or establish that the conceptual interpretation of a node is correct.

### 12.3. Subgoal accounting and axiom-detection controls

The action-to-plan binding gate now additionally checks compositional subgoal accounting: the multiset of goals emitted by `A_SPLIT_IFF` must equal the multiset of downstream action input goals, exactly two outputs must exist, and output IDs must be unique. A generated manifest mutation omitting `G_REVERSE` must be rejected.

A second pinned Lean negative fixture, [ProofActionCertificateAndCommAxiomNegative.lean](../../scripts/research/lean-proof-extractor/ProofActionCertificateAndCommAxiomNegative.lean), introduces an explicit axiom and proves a deliberately axiom-dependent proposition. This is not offered as a valid certificate. Instead, the workflow requires `#print axioms` to report the exact injected axiom name and records the source/log digests. This demonstrates detection of one known axiom dependency; it does **not** yet parse or exhaustively classify every axiom, unsafe, partial, opaque or admission path.

The exact-head workflow must pass the subgoal omission rejection, wrong-proposition type-error rejection, and injected-axiom observation before the action certificate receipt can be emitted.
