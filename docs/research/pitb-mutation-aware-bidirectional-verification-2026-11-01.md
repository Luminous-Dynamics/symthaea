# PITB research track: mutation-aware, bidirectional program verification (2026-11-01)

**Priority:** P0 research extension beside Aegis; not an Aegis leaderboard result.  
**Status:** protocol proposal only. No Rust/Aeneas mutation cohort has been generated or evaluated by PITB.

## The research opening

Aegis is unusually valuable because it asks whether an agent can prove a frozen property P or prove its negation not-P about a translated implementation. The task-generation pipeline requests properties intended to hold and properties intended to fail. The result can therefore test both proof production and whether the specification generator correctly expressed the requested behavior.

The Aegis paper also says it created mutated program variants to generate additional tasks, but did not evaluate those mutation-generated tasks. This creates a clear next research question: can PITB reliably track how a source-level implementation change changes the admissible specification and proof/refutation outcome?

This is not just another theorem-completion benchmark. It measures whether a system preserves the relationship between:
1. source implementation identity;
2. Rust-to-Lean translation identity;
3. intended program semantics;
4. frozen specification bytes and requested polarity;
5. the accepted proof or refutation.

A proof against the wrong program version, or of the wrong polarity, is a failure even if Lean accepts the proof term.

## Published Aegis facts and important limits

The 28 October 2026 preprint reports EasyProver using the off-the-shelf Anthropic Fable-5 model without fine-tuning or a separately trained policy/value network. Its harness uses recursive isolated agents, asynchronous search, parallel tactic probing and the stateless InfiniLean elaboration service. It caps active sub-agents at 64 and concurrent expensive Lean queries at 16; the hardest proofs used more than 300 sub-agents over a run. The system rechecks promoted candidates with a separate Lean Comparator, freezes the target signature and checks the axiom allowlist. Sources: https://arxiv.org/abs/2610.38174 and https://arxiv.org/html/2610.38174.

The Aegis pipeline starts from public LeetCode problem descriptions, generates safe Rust implementations, runs Rust tests, extracts/translates with Charon/Aeneas, checks differential Rust/Lean behavior, and then generates properties requested to hold or fail. Of 2,356 attempted program implementations, 2,045 (86.8%) passed Rust testing, extraction, translation, Lean elaboration and differential evaluation. The sample of 2,000 specifications is stratified across 1,257 translated programs; EasyProver proves 1,054 (52.7%) within 30 minutes per statement. The 2,000-task proof sample excludes the full 11,533-candidate denominator, and the paper's model training cutoff is not public. The Aegis statements themselves were generated by the pipeline and did not predate the work.

Aegis uses an optional Plausible counterexample screen on requested-to-hold statements. It supplies no positive labels: finding no counterexample does not count as proof. A property requested to hold is confirmed by proof of P; a property requested to fail is confirmed by proof of not-P. The opposite polarity is a mismatch. Source: paper sections 3.2 and 4, https://arxiv.org/html/2610.38174.

The arXiv paper page does not link a dedicated public Aegis code/data repository in its current references. I did not find an author-linked Aegis repository in the GitHub repository search during this research pass. PITB should request the exact 2,000-task sample and its license from the authors before describing any local recreation as a direct reproduction. The public problem descriptions and an independently reconstructed generator can support a separate Aegis-inspired cohort, not an identical leaderboard comparison.

## New PITB cohort: implementation mutation pairs

Create a mutation pair from one validated source implementation:

- **Original:** pinned Rust source, Cargo lock/toolchain, function signature, reference-test manifest and Aeneas Lean extraction.
- **Mutant:** a single reviewed source mutation with exact patch and mutated-source digest, independently compiled and translated to Lean.
- **Differential records:** Rust and Lean outputs for each version on the same test-input manifest. Every Rust result must match its own Lean translation. The mutant is not required to behave like the original; its expected behavioral delta must be declared and witnessed.
- **Specification pair:** frozen original and mutant propositions with exact source-program binding and requested polarity.
- **Proof/refutation pair:** a kernel-checked proof of the expected proposition or its negation, with the exact program-version and proposition digests.

A task must never mix an original-program proposition with a mutant-program proof or refutation.

### Initial mutation operators

Begin with deterministic, single-site, behavior-changing mutations that have a concrete witness:

| Operator | Typical semantic change | Example obligation |
|---|---|---|
| Boundary off-by-one | Accept/reject one boundary input | Output bound or indexing safety |
| Comparison flip | Change strict to non-strict comparison | Loop termination / range |
| Arithmetic operator | Change addition to subtraction or multiplication to division | Exact functional result |
| Narrowing cast | Change width or truncation behavior | Numeric range and conversion |
| Loop bound | Change exclusive/inclusive bound | Collection length / iteration count |
| Index shift | Change index i to i+1 | Bounds and element correspondence |
| Error-path mutation | Remove or alter a failure branch | Totality and error semantics |
| Guard removal | Remove precondition or validation | Safety invariant / failure behavior |
| Return mutation | Change a terminal value or branch result | Functional correctness |
| State-update mutation | Alter vector/list update or write-back | Length preservation / mutation invariant |

Do not begin with arbitrary multi-site mutants. They confound attribution and create ambiguous expected outcomes. Add multi-site variants only after single-site operators have calibrated sensitivity and false-positive behavior.

## Bidirectional scoring

Keep four output classes separate:

1. **Expected polarity proved:** a kernel-checked proof matches the requested behavior for the exact original or mutant.
2. **Expected polarity refuted:** a kernel-checked proof of the negation matches a specification requested to fail.
3. **Opposite polarity:** a kernel-checked proof exists, but it contradicts the request. Count as a specification mismatch, not success.
4. **Unresolved/abstained:** neither polarity is proved within budget, or target integrity is pending.

A refutation must include the frozen proposition identity and Lean proof of its negation. A test failure or Plausible counterexample is useful screening evidence, but is not itself a kernel proof of the negation.

## New research questions

- **Mutation sensitivity:** does a one-line implementation change cause the system to update its invariant, premise route and expected proof/refutation polarity?
- **Version isolation:** can the agent accidentally reuse a proof from the original program against a mutant or vice versa?
- **Specification repair:** can PITB identify that a previously correct property is no longer correct, then generate a revised target without silently weakening the old one?
- **Counterexample-guided abstraction:** can the system convert a counterexample into a minimal changed precondition/invariant while retaining the exact source binding?
- **Transfer:** do support antichains and typed repair learned on one mutation operator transfer to an unseen operator, program family or later source snapshot?

This turns failed attempts and refutations into structured supervision about which semantic assumptions changed, rather than treating every failure as a prompt to spend more tokens.

## Evaluation design

Keep original and mutation cohorts separate in all summary tables:

| Cohort | Primary question | Primary metric |
|---|---|---|
| Published Aegis sample | Can PITB reproduce/beat the reported prover on the same frozen tasks? | Exact polarity resolution within 30 minutes |
| Aegis-inspired original cohort | Can the generation pipeline create harder, auditable implementation obligations? | Validated specs per source program; polarity resolution |
| Single-site mutation cohort | Does the system correctly adapt to implementation changes? | Correct polarity resolution on original/mutant pairs |
| Unseen-operator transfer | Does learned proof insight transfer to mutation types absent from development? | Component-clustered held-out pair accuracy |
| Version-confusion adversarial set | Does the prover reject cross-version and cross-statement evidence? | Zero false accepts |

Use intention-to-treat denominators at the original source-program component level. Keep all generated mutants, rejected translations, invalid specs, unattempted tasks and unavailable-tool results visible. Do not drop a mutant after it proves inconvenient. Resample by source program, not by individual specification, because many statements share a single implementation.

### Required gates

- Exact original/mutant Rust source bytes, Cargo lock and toolchain.
- Exact Charon/Aeneas versions and extracted Lean module bytes.
- Independent Rust and Lean differential results on the same test manifest.
- A concrete, pinned witness for behavior-changing mutations.
- Exact statement digest and requested polarity.
- Target-integrity receipt with signed reviewer attestation and axiom policy.
- Exact proof/refutation artifact, kernel checker receipt and independent clean replay.
- Proof/refutation target version must match the same original or mutant source identity.

## Qualification targets (research goals, not results)

- 100% of accepted proof/refutation receipts bind the exact source variant, translated module and target proposition.
- Zero cross-version or wrong-polarity false accepts across adversarial mutation controls.
- ≥90% correct polarity classification on a reviewed, held-out single-site mutation subset.
- ≥80% recall for detecting behavior-changing mutations at ≤5% false-positive rate on the mutation-screening stratum.
- ≥10 percentage-point transfer improvement on unseen mutation operators over the matched fixed-step baseline, at equal budgets.
- ≥20% lower cost per correct polarity resolution than a matched full-context baseline, without semantic-integrity regression.

These are stretch targets. The first defensible result may be zero cross-version false accepts with a modest solve rate, not an inflated score over a small handpicked mutant set.
