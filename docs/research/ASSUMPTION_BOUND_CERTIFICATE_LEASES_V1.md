# Assumption-Bound Certificate Leases v1

**Status:** deterministic software-lifecycle prototype; not a formal proof or physical safety certification.

## Problem

A robust action can be correctly certified at one point in time and become uncertified after its assumptions change. A state estimate may update, the dynamics model may be replaced, the safety limits or calibration may change, emergency authority may be revoked, new monitor evidence may trigger a fallback, or the supporting evidence itself may be superseded. If a caller retains a boolean or action mask without a machine-checkable context, stale approval can be accidentally reused.

This work treats a safety certificate as a **short-lived capability bound to its assumptions**, rather than a bare "safe" flag. It is related to dynamic safety cases and runtime assurance, but this small implementation does not reproduce a broader safety-case framework.

## Lease context

A lease is created only when the requested action appears in a multi-step viable-action set whose horizon exactly matches the issuance context. The context records:

- decision step and state-estimate revision;
- dynamics-model revision;
- safety-limits revision;
- calibration revision;
- action-authority revision;
- monitor epoch;
- certified horizon;
- digest of the supporting evidence.

A nonzero 32-byte digest is required. The digest itself must be generated by the caller from the declared evidence bundle; the type does not independently hash source data or verify a cryptographic signature.

The certificate has an explicit expiry step. Lease age must be shorter than the certified horizon; the intended control-loop default is age zero, followed by recertification after each new transition. A caller can use a larger age only if it can guarantee that the state revision and every other context value remain unchanged.

## Validation behavior

Validation succeeds only when the requested horizon does not exceed the certified horizon, the lease has not expired, time has not moved backward, and all state/model/limits/calibration/authority/monitor/evidence identifiers match exactly.

A mismatch produces a typed rejection reason. The caller must transition back to certification rather than keep executing the cached action. In particular:
- changed monitor epoch invalidates the old certificate even if the same action is still available;
- changed authority revision invalidates a certificate relying on emergency recovery permission;
- changed calibration or evidence digest invalidates a certificate based on the old uncertainty envelope;
- a longer requested horizon cannot reuse a shorter-horizon certificate;
- expired or time-rewound leases are not accepted.

The module does not decide which recovery action to take after rejection; that remains the responsibility of the caller's verified runtime-assurance path. A rejection is not proof that the previously permitted action would have been unsafe; it means the old certificate can no longer justify permitting it.

## Files and qualification

- `src/certificate_lease.rs`: validated context, issuance from a horizon-certified action set, expiry, typed invalidation reasons and unit tests.
- `src/bin/allostatic-certificate-lease-bench.rs`: 13 deterministic lifecycle cases covering unchanged context, state/model/limits/calibration/authority changes, monitor and evidence changes, expiry, clock regression, horizon enlargement, uncertified action issuance, and zero-digest rejection.
- Exact-head qualification adds byte-identical reruns, row/schema/status gates, output digests and source digest coverage.

The benchmark is a contract test: its expected reason is independently specified in the test manifest. It does not validate real source digests, revision counters, time sources, cryptographic identity, or integration with a live control loop.

## Proposed next steps

1. Generate evidence digests and monotonic revision IDs from the actual evidence/model/configuration pipeline, not from arbitrary caller values.
2. Bind the lease to the independent verifier's receipt, reachable-set witness, and search-budget completion record.
3. Test race conditions and TOCTOU behavior between certificate validation and action application.
4. Ensure state, authority, monitor and model revision changes invalidate cached permission atomically.
5. Add a model checker or exhaustive state-machine test for the lease lifecycle, including counter wraparound, resets, stale telemetry, and reboot/recovery boundaries.
6. Integrate with external pinned control tasks and measure decision overhead and stale-certificate rejection behavior.

## Claim boundaries

This does not prove a reachable set is sound, that the environment lies inside the uncertainty envelope, or that the supplied digest corresponds to valid evidence. It prevents certain classes of stale-certificate reuse if callers faithfully update the context values. The live Symthaea control loop is not changed by this research branch, and no SOTA claim is made.
