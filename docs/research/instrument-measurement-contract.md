# Instrument Measurement Contract

**Status:** research engineering contract; not a medical device or clinical validation.  
**Crate:** `symthaea-instrumentation`  
**Scope:** scalar measurement envelopes, raw-data and calibration-evidence resolution, freshness, quality gates, and stream ordering.

## Why this is a separate crate

Ultrasound is the first use case, but calibrated measurements are cross-cutting. Keeping the contract in a dependency-light crate avoids coupling a generic evidence envelope to acoustic equations or the robotics physics backend. Domain crates should translate their native data to this envelope at the adapter boundary instead of duplicating provenance rules.

## Envelope requirements

Each measurement binds:

- instrument and channel identifiers (not patient identity); the assessment receipt retains this identity and the named clock epoch;
- monotonically sequenced acquisition, a monotonic timestamp, and an explicit `ClockDomainId` naming the clock origin/epoch;
- explicit quantity and unit, checked for dimensional compatibility;
- finite value and non-negative standard uncertainty in the declared unit;
- a version/digest identifying the processing chain;
- optional raw-data and calibration references, each identified by an ID and SHA-256 digest;
- explicit acquisition-quality flags.

The initial unit set covers common engineering signals and research-healthcare prototypes: distance, time, frequency, acoustic pressure, temperature, electrical potential/current, heart rate, respiratory rate, dimensionless percentages and explicitly typed oxygen-saturation percentages, speed, acceleration, angular velocity, sound-pressure level referenced to 20 µPa, and dimensionless values. Values are never silently converted. Extending the unit vocabulary requires an explicit quantity mapping and tests.

## Fail-closed quantitative gate

The strict assessment checks sequence/time ordering using a caller-maintained `MeasurementStreamGuard`; resolved raw-data metadata can now be constructed only from a `VerifiedArtifactDigest`, rather than a caller-provided digest string and byte count. Calibration resolvers must return `VerifiedCalibrationEvidence`, pairing the record with byte-verified certificate and review receipt whose artifact references match the record. These types enforce byte-digest checks, non-empty calibration/review content, and reference binding, not semantic interpretation or signing authority. The gate also requires the uncertainty policy's unit to exactly match the measurement unit (no implicit conversion) and rejects:

- mismatched clock-domain context, future-dated or stale data;
- any declared quality flag (saturation, motion artifact, lead-off, missing samples, unsynchronized clock, failed self-test, out-of-range values, unknown signal quality, etc.);
- missing raw-data or calibration references;
- raw acquisition bytes that cannot be resolved, are empty, or do not match the envelope's artifact ID/digest;
- unresolved calibration evidence;
- resolver results whose calibration record ID or evidence artifact differs from the measurement reference;
- calibration evidence for a different instrument/channel, quantity/unit, validity interval, or calibrated value range;
- measurement or calibration uncertainty above the consumer's explicit limits. Both limits and both uncertainties are interpreted in the same explicit unit; use a separately reviewed conversion before assessing a different unit.

The raw-data and calibration resolvers are explicit trust boundaries. The raw-data resolver must actually retrieve the referenced bytes, compute/verify their digest, and return non-empty artifact metadata; merely looking up a database row or echoing the supplied reference is insufficient. The calibration resolver must resolve and review artifact bytes/digests, the review receipt, exact instrument/channel identity, supported quantity/unit, validity dates, inclusive calibrated value range, calibration chain and uncertainty contributions. The strict gate rejects a calibration record for another channel or a measured value outside the stated range. The crate checks returned IDs/digests against the observation, but cannot prove either resolver is independent or authoritative by itself. Configure and test both implementations independently. The returned `MeasurementAssessment` is read-only through its public API and retains the instrument, timestamp domain, observed value, calibration evidence/review references, parsed provider/procedure IDs, reference-standard artifact identity, reviewer-authorization proof (including its exclusion list, policy digest, authenticated trust-snapshot sequence/digest, authority-key fingerprint, and verification time), calibrated range, raw artifact metadata/source-version ID, and uncertainty limits that passed. It is not a cryptographically signed receipt or clinical authorization.

Measurement and calibration standard uncertainties are reported separately. The crate does not combine them by root-sum-square because doing so requires explicit assumptions about independence and all material uncertainty contributors. Traceability is a property of a measurement result connected through an unbroken, documented calibration chain in which each link contributes to uncertainty; a certificate reference alone does not establish traceability.

## Shared content-integrity primitive

The crate exports `VerifiedArtifactBytes`, `VerifiedArtifactDigest`, `ImmutableArtifactReader`, and `sha256_hex` so adapters can verify content against an `ArtifactReference` using one implementation. The byte wrapper retains the verified bytes so a parser can consume those bytes instead of reopening a mutable path. The streaming verifier hashes incrementally with a bounded buffer and returns the checked reference plus byte length without retaining a second copy. Its integrity-only API is deliberately insufficient for `ResolvedRawData`: adapter readers must implement `ImmutableArtifactReader`, binding reads to one immutable object-version or content-snapshot identifier and asserting that the source object ID matches the requested artifact reference. Resolved metadata retains that identifier for later retrieval, and mutable path reads or latest-version aliases must not implement this contract. Eleven unit tests cover a standard SHA-256 vector, byte/reference retention, one-byte mutation, empty-content behavior, multi-chunk streaming, streaming tampering, interrupted-read retry, and reader failure. The 38 measurement-contract integration tests exercise the shared primitives for raw acquisitions, calibration certificates, reference-standard certificates, and review receipts. They reject wrapper/reference mismatches, substituted reference-standard bytes, certificate/metadata disagreement, and a correctly hashed review receipt that binds a different certificate digest.

This primitive establishes content integrity relative to a supplied digest only. It does not authenticate the source, verify a signature, bind a parsed claim to a certificate, establish reviewer independence, or make a review receipt authoritative. `VerifiedArtifactBytes` owns a full byte buffer; `VerifiedArtifactDigest::verify_reader` is the bounded-memory option for large acquisitions. Because the streaming result does not retain the bytes, an adapter must use the returned immutable source-version identifier for all later reads and fail closed if that version is unavailable. The trait is an adapter contract, not cryptographic proof that the backend truly pins an immutable version; production qualification must audit that binding.

## Canonical calibration certificate claims

The research format `symthaea.calibration-certificate.v1` encodes record ID; instrument and channel; quantity and unit; inclusive range bounds; validity interval; standard uncertainty; calibration provider and procedure IDs; and a reference-standard artifact ID plus SHA-256 digest. Its parser rejects missing/reordered/extra fields, alternate numeric encodings, incompatible quantity/unit pairs, invalid ranges/windows, non-finite values, and control characters in identity fields. The format is a canonical contract for this crate, not a claim of conformity to an external calibration-certificate standard.

`VerifiedCalibrationEvidence::new` parses the exact digest-verified certificate bytes and checks the record ID, instrument/channel, quantity/unit, range, validity interval, and uncertainty against `ResolvedCalibration`. It also parses the first referenced standard as a canonical certificate, requires its record ID to match the referenced artifact ID, and requires exact quantity/unit agreement with the calibration certificate. Non-empty, digest-verified bytes for that standard and a cryptographically verified review receipt bound to the exact parent certificate and record are mandatory. Parsed claims and verified standard bytes remain available to downstream review/traceability logic. Integration tests include mismatched resolved ranges, substituted standard objects, and a standard certificate for the wrong quantity.

**Time-basis limitation:** the existing quantitative gate represents `valid_from_ns`/`valid_until_ns` in the same nanosecond basis as `MeasurementEnvelope.captured_at_ns`. Those values are not UTC timestamps and do not by themselves express calibration validity across rebooted clock epochs. Do not interpret this research schema as a production-ready, interoperable calibration certificate until the temporal basis is made explicit and wall-clock certificate validity is bound to a trusted capture-time representation.

The six certificate-parser unit tests cover canonical round-trip, rejected field order/extra fields, alternate number forms, invalid unit/range pairs, control-character injection, and claim-binding for the record/instrument/unit/range/validity/uncertainty fields. The 36 integration tests cover mismatched metadata and reference-standard substitutions. The first reference-standard certificate is parsed and bound, and its declared range and validity interval must cover the dependent calibration. However, the current format does not recursively resolve/verify that standard's parent reference, independently verify that standard certificate's own review receipt, or validate the complete calibration chain. The local range/time containment rule establishes scope consistency only, not traceability or provider competence. A production resolver must establish each traceability link, its stated uncertainty contribution, the calibration method, applicable conditions, and the authority/competence of the relevant provider. NIST describes metrological traceability as a documented, unbroken chain in which each calibration contributes to uncertainty; a certificate or standard reference by itself is insufficient.

## Signed calibration review receipts

The crate also defines a canonical `symthaea.calibration-review.v1` receipt. The Ed25519 signature covers a domain-separated, ordered payload containing the reviewer key ID, calibration record ID, certificate artifact ID and SHA-256 digest, and issuance/expiry timestamps. The envelope has one canonical encoding; alternate field order, extra fields, uppercase/non-canonical signature hex, and malformed encodings are rejected.

`SignedReviewTrustStoreSnapshot` has a canonical binary encoding and strict parser. Its v2 root signature covers the complete ordered trust snapshot, including sequence, issue/expiry window, reviewer public keys, reviewer identities and organizations, validity periods, and revocation state. `SignedReviewTrustStoreSnapshot::verify` accepts only an out-of-band pinned authority public key and returns `VerifiedReviewTrustStore`; the receipt verifier does not accept raw, unauthenticated trust-store objects. `VerifiedCalibrationReviewReceipt::verify` checks canonical bytes, record/certificate binding, trust freshness, lifecycle rules, and the strict Ed25519 signature, but does not authorize the signer for calibration approval. `VerifiedCalibrationReviewReceipt::verify_for_calibration` additionally requires reviewer identity and organization from the root-signed v2 snapshot, and returns a policy-bound authorization proof. `VerifiedCalibrationEvidence::new` rejects a crypto-only receipt and checks that the proof's provider matches the parsed certificate provider. The store rejects empty/oversized/duplicate key sets and requires a nonzero sequence plus a bounded validity window. The guard rejects a lower sequence and reuse of the same sequence with different snapshot contents; repeating the exact latest snapshot is idempotent. Candidate state is checked before signature verification but committed only after a receipt verifies successfully, so an invalid receipt cannot advance the guard. It can export/restore a `(sequence, digest)` checkpoint for durable state, but the deployment must authenticate the checkpoint when loading it. Verification rejects stale trust snapshots, unknown or revoked signers, duplicated public-key aliases, receipts that are not yet valid or expired, and keys that were not valid when the receipt was issued. Revocation is fail-closed at verification time, including for previously issued receipts.

The v2 signed snapshot authenticates reviewer identity and organizational affiliation along with trust-store contents relative to the configured authority key, but that root key is not self-authenticating. Deployments must provision and rotate the root key securely, persist and authenticate the guard's highest-sequence/digest checkpoint across restarts, refresh the signed snapshot before expiry, and document key rotation and revocation policy. A new in-memory guard has no prior history and cannot detect rollback across process restart by itself. The v2 canonical trust snapshot binds reviewer identity and organization along with lifecycle data; its parser rejects partial identity tuples, reordered fields, duplicate keys, invalid option encodings, trailing data, and non-canonical byte representations. Receipt signatures prove that the configured key signed the canonical claims. The authorization policy applies an organizational-separation rule against the provider and configured conflicts, but cannot establish that registry entries are truthful, that the reviewer is competent, or that the certificate's claims are accurate. The production adapter must still provision and rotate the externally pinned trust authority key, enforce reviewer role/authorization and independence, validate provider competence and the complete traceability chain, and obtain updates from a separately governed authority. The certificate's provider/procedure/reference-standard claims are content-bound but not authoritative merely because they parse.

Nineteen unit tests cover canonical round-trip and valid signature, signature tampering with a recomputed artifact digest, unknown/revoked/expired signer paths, trust-snapshot and receipt expiry, record/certificate binding, empty receipt rejection, duplicate public-key aliases, non-canonical encoding rejection, trust-store sequence advancement, rollback rejection, same-sequence substitution, checkpoint restore, ensuring an invalid signature does not advance trust state, canonical trust-store bytes round-trip, signed trust snapshots round-trip, and snapshot mutation or a wrong root authority is rejected. The integration suite also exercises signed review receipt verification through the calibration resolver.

## Production resolver admission gate

The test double is an interface-level control, not evidence that a deployed resolver is trustworthy. Before a production resolver can support a quantitative-use claim, qualify the resolver implementation separately against this admission gate:

1. **Retrieve bytes, do not echo metadata.** Resolve certificate, referenced standard evidence, review receipt, and raw acquisition from a governed source; hash the exact retrieved bytes (streaming is acceptable) and compare them with the referenced digests. A database row, manifest string, or claimed digest is not a substitute for reading the artifact.
2. **Bind parsed claims to the content.** Verify that the certificate content binds the expected record ID, instrument and channel, quantity/unit, calibrated range, validity interval, calibration procedure, reference standards/traceability chain, and uncertainty statement. The directly referenced standard certificate must also cover the dependent calibration's full range and validity interval; this containment check is not recursive chain validation. Returned metadata must be derived from the verified artifact, not independently edited fields that merely happen to share an artifact ID.
3. **Verify and authorize the reviewer independently.** Hash the review-receipt bytes and verify its signature/authority against a trust anchor configured outside the artifact being checked. The v2 root-signed trust snapshot binds each review key to a reviewer identity and organization. Use the calibration-specific verifier with a policy derived from the parsed certificate provider, and exclude that provider plus configured related-party organizations. Verified calibration evidence rejects signature-only receipts without this proof. Organization identifiers must come from a separately governed registry; organizational separation is a necessary filter, not proof of competence or absence of every conflict of interest. Preserve reviewer identity, approval time, the canonical exclusion list and authorization-policy digest, expiry, and revocation state in the qualification record.
4. **Reject substitution and time-of-check gaps.** For raw acquisitions, require the streaming reader to expose the immutable object-version or snapshot identifier that supplied the bytes, and retain that identifier with the digest result. Fail closed on mutable path reads, an unavailable pinned version, mutated bytes, a same-digest/different-ID substitution where identity is significant, a receipt for another certificate, stale trust/revocation state, expired or revoked credentials, missing objects, parse failures, and store/network errors. Do not silently fall back to cached or ambient trust data without a separately specified freshness policy.
5. **Exercise positive and negative fixtures.** Keep stable positive fixtures with known SHA-256 values. Include a one-byte mutation for each artifact, wrong certificate binding, wrong channel/range/time, review-to-wrong-certificate binding, duplicate/reused review, revoked or unauthorized reviewer, unavailable resolver, and corrupted trust bundle. Assertions should check the precise fail-closed class, not just that some error occurred.
6. **Preserve the qualification receipt.** Record the resolver implementation/version, exact source revision, trust-bundle digest, artifact IDs and computed digests, policy version, fixture corpus, and completed test-run identifiers. The receipt must point to completed results for the exact source head; queued jobs are not evidence of a pass. Avoid logging raw acquisition bytes or unnecessary patient-linked metadata.

Admission decision: CI is necessary but not sufficient. The production resolver remains unqualified until its own integration tests and trust-store/key-management review cover these controls. The crate's `MeasurementAssessment` alone cannot attest to them.

## Stream ordering

`MeasurementStreamGuard` keeps the highest consumed sequence and the last accepted non-future timestamp per instrument/channel. Repeated or lower sequences are rejected without changing state. A newer sequence with a backward or future timestamp is consumed, but the last accepted timestamp remains unchanged; retrying that sequence cannot turn the rejected sample into an accepted replay, and a future-dated sample cannot poison the timestamp high-water mark. Every envelope carries a `ClockDomainId`; the gate requires the caller's current-time reference to use the exact same ID, so monotonic values are not compared across unrelated clock origins. A reboot/reset should get a new clock-domain ID, and an existing in-memory stream guard rejects a domain change rather than silently comparing the new epoch with old timestamps. An epoch transition therefore requires controlled reconstruction of the guard from an authenticated checkpoint or a newly established stream identity; simply clearing state is not evidence of a safe reset. Callers must use documented, appropriately synchronized clock sources; the ID check is not a clock synchronization service. The quantitative-use API requires the guard and advances its sequence state as soon as an envelope reaches the gate—even if subsequent quality or calibration-evidence checks reject it. This is intentionally conservative and means the source must send a new sequence after any rejection. The guard is in-memory, not a tamper-proof replay ledger; safety-sensitive deployments must persist/reconcile stream checkpoints across restarts and authenticate the source.

## Validation strategy

1. Unit tests reject bad dimensions, non-finite values, negative uncertainty, malformed identifiers and digests.
2. Gate tests exercise freshness, quality flags, clock epochs, absent provenance, unresolved raw/calibration artifacts, evidence mismatch, instrument/channel mismatch, wrong units (including the uncertainty-policy unit), validity windows, calibrated-range enforcement and uncertainty limits.
3. Clock-domain tests verify mismatched caller clocks fail before consuming stream state and unexpected source epoch changes are rejected by an existing guard. Raw-evidence tests exercise empty artifacts, unresolved acquisition bytes and artifact-ID/digest mismatch. Certificate tests reject non-canonical encodings, incompatible units, invalid ranges, and identity-control characters. Calibration integration fixtures use a canonical certificate, reference-standard bytes, and a signed review receipt; tests reject digest mismatches, a substituted standard, incorrect certificate-to-metadata claims, and reviews bound to another certificate. These fixtures validate the mock adapter only, not a production evidence store.
4. Stream tests exercise duplicate/replayed sequence numbers, time reversal and rejection of future timestamps without poisoning the accepted timestamp floor.
5. In the next integration step, connect this contract to synthetic biomedical signals and ultrasound simulator output, then use independently generated raw-acquisition and calibration-review fixtures. The current crate does not acquire hardware or claim a clinical use is safe.

```sh
cargo test -p symthaea-instrumentation

```

## Research and standards foundations

- [NIST — Metrological Traceability](https://www.nist.gov/metrology/metrological-traceability): traceability requires a documented unbroken calibration chain, with uncertainty contributions at each link. NIST also cautions that traceability alone does not guarantee fitness for purpose.
- [NIST — Measurement Uncertainty](https://www.nist.gov/glossary-term/39291): uncertainty is a non-negative parameter describing dispersion attributable to a measurement result.
- [DICOM PS3.17 — Specification of Standard Measurements](https://dicom.nema.org/medical/dicom/current/output/chtml/part17/sect_DDDD.2.html): standard measurement definitions need enough detail for consistent acquisition and interpretation. This contract is not a DICOM implementation.
- [IMDRF — Good Machine Learning Practice for Medical Device Development](https://www.imdrf.org/documents/good-machine-learning-practice-medical-device-development-guiding-principles): relevant lifecycle and data-quality principles for future ML-enabled features.
- [FDA — Quality Management System Regulation](https://www.fda.gov/medical-devices/postmarket-requirements-devices/quality-management-system-regulation-qmsr): became effective on 2 February 2026 and incorporates ISO 13485:2016 by reference for the U.S. device quality-system framework. This note is engineering guidance, not a jurisdiction-specific compliance determination.
- [SAHPRA — Medical Device and IVD Guidance](https://www.sahpra.org.za/medical-devices/): South African regulatory context must be checked against the specific intended use and current applicable guidance before any clinical or commercial deployment.

## Privacy boundary

No patient identifier is part of the envelope. Raw acquisition references can still resolve to sensitive medical data; real integrations must apply access control, encryption, retention limits, audit logging, and appropriate de-identification/consent controls before research reuse. The test fixtures use synthetic identifiers and values, not patient records.

## Explicit non-claims

This contract does not establish diagnostic accuracy, sensor calibration authenticity, metrological traceability by itself, acoustic exposure safety, image quality, patient safety, regulatory conformity, or clinical efficacy. Quantitative assessment is only one evidence gate in a larger intended-use and safety case.
