# Independent Certificate Verifier v1

**Status:** deterministic synthetic contract experiment; no formal or physical safety claim.

## Research question

Can a safety certificate generated by the planner be checked by a smaller, structurally separate verifier that never calls the planner's recursive search or transition helpers?

This is the next layer after bounded viability, assumption-bound certificate leases, OOD fallback, and safe active falsification. The planner can search for a safe continuation, but its own action-set bit is not an independent witness. A useful separation is:
- a candidate generator searches and emits a complete sequence of actions;
- a certificate lease binds the requested first action and sequence horizon to state/model/limits/calibration/authority/monitor/evidence revisions;
- an independent checker recomputes every interval transition from primitive effect bounds and checks every intermediate constraint;
- execution is permitted only if freshness and witness verification both accept.

This idea complements certificate synthesis/verification research rather than replacing it. Relevant references include the review of dynamical-model certificate synthesis (Annual Reviews in Control, 2025), data-driven certificate synthesis (Automatica, 2026), verification-guided shielding for deep RL, and the survey "Shields for Safe Reinforcement Learning":

- https://software.imdea.org/~cesar/publication/2024-corsi24verification/

## Verifier contract

`src/independent_verifier.rs` does not call the planner's `safe_transition`, `next_state_envelope`, or horizon search. It implements a separate endpoint propagation path and checks:
- nonempty sequence;
- valid and exact requested horizon;
- initial state inside the declared constraints;
- emergency-action authority at each step;
- finite interval arithmetic;
- reserve and load constraints after every transition.

A later safe state cannot erase an earlier violation. The checker returns either a receipt recording the initial/final interval, first action and verified step count, or a typed rejection reason.

`verify_leased_witness` composes this check with the assumption-bound certificate lease. It rejects a stale context, a witness whose first action differs from the leased action, a witness with the wrong horizon, and an unsafe transition sequence. On success it returns a `VerifiedActionPermit` with private fields, issued only after both checks pass; the permit exposes the action, verification receipt, expiry, decision step and evidence digest. A live control adapter should require this token at its action-application boundary instead of accepting a naked action enum. The permit retains the original lease and exposes `validate_for_use(current_context)`; the executor should call this immediately at the action-application boundary. Validation/application must still be atomic or TOCTOU-tested: the token cannot protect the system if the caller ignores it or changes the plant/model context without changing the bound identifiers.

## Differential test

The unit tests enumerate all open-loop action sequences over a small state/dynamics grid for horizons 1 through 4. For each candidate first action, the independent checker searches for a complete safe sequence by exhaustive enumeration and compares that result with the planner's horizon viable-action set. That exercises the set relation without reusing the planner's search routine. The fixture also compares independent one-step results against the one-step evaluator.

The standalone deterministic benchmark contains 11 cases:
1. complete safe multi-step witness;
2. unsafe first transition;
3. unsafe intermediate transition followed by recovery;
4. missing emergency authority;
5. supplied sequence/horizon mismatch;
6. initially unsafe state;
7. fresh leased certificate plus valid witness;
8. stale dynamics revision;
9. changed supporting-evidence digest;
10. altered first action;
11. transition that disagrees with the claimed model even when the harness intentionally supplies unchanged metadata.

The final case is an integration negative control: it demonstrates that the arithmetic checker can reject an unsafe supplied transition, but it also documents a remaining trust boundary. Real integration must derive the dynamics revision and evidence digest from the exact actual model/evidence object; a caller that lies about those identifiers can defeat freshness semantics even when the type system is correct.

## Metrics and qualification

The qualification script runs the verifier suite twice, requires byte-identical raw and summary outputs, checks every expected verdict and row, records the source and output digests, and preserves the outputs as workflow artifacts. The exact-head workflow must pass formatting, tests and Clippy before the benchmark's contract results count as qualified.

For external tasks, extend the witness format to carry the exact uncertainty set, reachable-set representation, control interval, constraints, action authority, search budget, and immutable provenance receipt. The independent verifier should have a separate implementation and dependency footprint from the planner; ideally, it should be small enough for bounded model checking or a mechanically verified implementation.

## Limits

- The state/action model is a two-dimensional synthetic interval system.
- The checker verifies the provided interval model, not whether the real environment is enclosed by it.
- Shared input types are not independent evidence that the values are truthful.
- The 11-case bench and small exhaustive grid are software tests, not physical validation or proof of SOTA performance.
- The lease and verifier do not by themselves eliminate TOCTOU races; enforcement must bind verification and action application atomically.
- No live Symthaea control loop is changed by this branch.
