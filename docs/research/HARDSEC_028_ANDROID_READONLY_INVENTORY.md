# HARDSEC-028 — Privacy-safe Android read-only inventory

**Status:** Rust ADB collector and injected-runner tests. It has not been run against a physical handset from this authoring environment.

Issue: [HARDSEC-028 / #9739](https://github.com/Luminous-Dynamics/symthaea/issues/9739)  
Parent mobile profile: [HARDSEC-027 / #9736](https://github.com/Luminous-Dynamics/symthaea/issues/9736) · [PR #9737](https://github.com/Luminous-Dynamics/symthaea/pull/9737)

## 1. What the collector does

The opt-in Rust example \`hardsec_android_readonly_inventory\` invokes a fixed allowlist of ADB shell commands and emits a \`hardsec-mobile-device-profile-v1\` JSON document.

It does **not** run \`adb devices\`, \`adb get-serialno\`, query IMEI/MEID/IMSI/ICCID, read Android ID, request location, read user data, or retrieve raw KeyMint certificate material. It never echoes ADB stderr because an ADB error can contain a device serial. If the ADB client cannot select a single device, collection fails with a generic error.

The only \`getprop\` keys queried are:

- \`ro.product.model\`
- \`ro.hardware\`
- \`ro.product.cpu.abi\`
- \`ro.build.version.release\`
- \`ro.build.version.sdk\`
- \`ro.build.version.security_patch\`
- \`ro.vendor.build.security_patch\`
- \`ro.boot.flash.locked\`
- \`ro.boot.vbmeta.device_state\`
- \`ro.boot.verifiedbootstate\`
- \`ro.build.fingerprint\` (digest only; raw value is discarded)

Optional probes are \`cat /proc/cpuinfo\` and \`simpleperf list\`. The CPU info is parsed in memory and only allowlisted feature names (\`mte\`, \`paca\`, \`pacg\`, \`bti\`) are retained as a normalized digest and coarse capability state. The raw CPU info is never written to the profile. \`simpleperf list\` records event names only; the collector does not invoke \`stat\` or \`record\`.

## 2. Reported properties are not attestation

The profile has separate properties for:
- \`reported_bootloader_lock_state\`;
- \`reported_verified_boot_state\`;
- cryptographically verified \`bootloader_locked\` and \`verified_boot_state\`;
- attestation security level, challenge freshness and certificate-chain status.

The ADB values populate only the *reported* fields. Cryptographic fields remain \`not_measured\`. They can be promoted only by a separately implemented and audited KeyMint attestation verifier.

This distinction is material: Android's attestation extension includes an attestation challenge, security-level fields, a RootOfTrust and separate software-/hardware-enforced authorization lists. Android documents that hardware-enforced authorizations are generated by the TEE or StrongBox rather than ordinary platform code. See the [Android Key and ID Attestation documentation](https://source.android.com/docs/security/features/keystore/attestation).

A future KeyMint workstream must generate a fresh unpredictable challenge, verify the certificate chain against trusted roots and revocation policy, check the challenge and RootOfTrust, and parse only the allowlisted claims needed for the profile. It must not request or export the attestation \`uniqueId\`, private keys, or raw certificates. This PR does not implement that verifier.

## 3. Capability is not process-level mitigation

If all parsed CPU \`Features\` rows advertise MTE, the profile reports \`hardware_support=on_device_reported\`. If feature rows disagree, it reports \`unknown\`. If a complete feature inventory lacks the feature, it reports \`unsupported\`. The process-level MTE \`runtime_state\` remains \`not_measured\` in every case.

Android's developer guide lists Pixel 8 Pro (Husky) among MTE-capable devices and describes checking for the \`mte\` CPU feature. It also distinguishes SYNC and ASYNC behavior. This does not, by itself, tell us which mode is enabled for a specific protected process. See the [Android MTE guide](https://developer.android.com/ndk/guides/arm-mte).

The collector treats Simpleperf similarly. A successful \`simpleperf list\` yields only an event-name inventory. It does not establish that a third-party process has permission to count an event, that the event can be scheduled without multiplexing, or that counter collection has acceptable observer effect. AOSP documents that Simpleperf uses Linux \`perf_event_open\` and that event availability varies by device/kernel. See the [AOSP Simpleperf introduction](https://android.googlesource.com/platform/prebuilts/simpleperf/+/557578b22806b54739e6426ed760bec9976aca05/README.md).

## 4. Operator procedure

From the repository root on a host with Rust/Cargo and Android Platform Tools installed:

\`\`\`sh
adb start-server
adb shell getprop ro.product.model
\`\`\`

The second command is only a manual readiness check; do not paste a full \`getprop\` dump into a public issue. Connect exactly one authorised test device. The collector intentionally does not accept a serial selector and does not enumerate connected devices.

Run the collector:

\`\`\`sh
cargo run --locked \\
  --manifest-path tools/hardsec-adaptive-evasion-audit-harness/Cargo.toml \\
  --features hardsec-android-readonly-inventory \\
  --example hardsec_android_readonly_inventory \\
  > android-mobile-profile.json
\`\`\`

If \`adb\` is not on PATH, set \`HARDSEC_ADB_PATH\` to the local ADB executable. The variable selects the executable path only; it is not interpreted by a shell.

Audit the generated profile locally:

\`\`\`sh
cargo run --locked \\
  --manifest-path tools/hardsec-adaptive-evasion-audit-harness/Cargo.toml \\
  --features hardsec-mobile-device-profile-audit \\
  --example hardsec_mobile_device_profile_audit \\
  -- --profile android-mobile-profile.json
\`\`\`

Before sharing a profile, inspect it locally. It contains model family, OS and patch level, a hash of the build fingerprint, selected reported boot properties, allowlisted CPU feature claims and Simpleperf event names. Do not append raw ADB logs, shell stderr, full CPU info, raw build fingerprint, raw certificates, or user files.

No changes are made to the phone: no root, no reboot, no property writes, no APK installation, no debug setting change, no PMU sampling run and no package modification.

## 5. Interpretation rules

| Collected value | What it supports | What it does not support |
|---|---|---|
| ADB boot properties | A software-reported bootloader/Verified Boot state | Verified RootOfTrust or trusted attestation |
| CPU \`Features\` rows | On-device-reported CPU feature capability | MTE enabled for a specific process, mode or allocator |
| Simpleperf event names | Tool-reported event inventory | PMU permission, counter scheduling, multiplexing or observer-effect qualification |
| OS/vendor patch properties | Reported patch level | Hardware-bound patch-level attestation |
| Build-fingerprint digest | Binding to a build fingerprint without exporting its raw text | Device identity or runtime integrity proof |

A missing property remains null/unknown/not measured. It is never converted to zero, false, or benign. A successful profile audit means the schema, privacy and provenance contract passed; it is not a security assessment of the handset.

## 6. Automated qualification

The isolated harness tests:
- property parsing and contradictory boot-property handling;
- MTE/PAC/BTI feature interpretation across heterogeneous CPU feature rows;
- Simpleperf event-name parsing without implying PMU access;
- raw build-fingerprint and CPU-info non-export;
- stable-identifier non-export;
- exact ADB command allowlist via an injected runner;
- generic failure behavior that never echoes a serial-containing error string.

The CI job does not require a physical phone. It tests the deterministic parsing and claim-ceiling contract. A physical acquisition will produce a profile with \`evidence_domain=physical_device_capture\`; the embedded Pixel fixture remains \`synthetic_fixture\`.

## 7. Claim ceiling

This tool establishes only a whitelist inventory of values visible to the ADB shell. It does not verify secure boot, authenticate the device, attest KeyMint/StrongBox state, prove runtime MTE enablement, qualify PMU measurement, measure thermal/battery/radio state, or prove resistance to physical or side-channel attacks.
