## Objective

A score edit should be a verifiable transaction, not an opaque mutation. Every candidate generated by the Sonata return adapter now carries a source-bound score patch receipt.

The receipt binds:
- the exact immutable source Score digest;
- the exact result Score digest;
- the source event count;
- the sorted, unique authorized source event indices;
- a stable source-revision event ID for every changed event;
- before/after digests for every changed ScoreNote;
- a digest of the complete protected complement outside the target;
- a canonical receipt digest.

The receipt is independently recomputable from the source Score, result Score and declared target set.

## Event identity without destabilizing the music-theory model

The current shared ScoreNote type has no intrinsic event identifier. Adding a required field to it would be a broad, potentially breaking schema change across every composer, importer, renderer and fixture.

v1 instead derives an event identity from a domain-separated identifier prefix, the immutable source Score SHA-256, and the original Score.notes vector index encoded as a fixed-width integer.

This identity is explicitly scoped to one immutable source revision. It remains stable as the note at that source index receives an in-place pitch or expressive-field update. It is not universal cross-revision identity and it does not establish musical ancestry after a move, insertion, deletion or reorder.

## Fail-closed v1 scope

The first version supports in-place note edits where event count is fixed and the target set is interpreted as source-indexed in-place updates. It rejects:
- score-level key, tempo, meter or total-duration changes;
- note insertion or deletion (event-count changes);
- duplicated or out-of-range target indices;
- any changed note outside the authorized target set;
- modified or stale receipt contents.

**Ordering limitation:** v1 does not infer event moves. A permutation that changes a protected index is rejected by the protected-complement check. A permutation wholly inside the authorized target set is represented only as per-index note changes; the current Score schema cannot distinguish that from in-place replacements. Therefore v1 must not be used to claim event-reorder lineage or preserved identity after moving events. A future lineage-aware patch schema must model explicit move and parent/child relationships.

Identical duplicate notes are indistinguishable under the current Score schema; the immutable source index is therefore part of the identity. Operations that insert/delete/reorder events need a richer lineage map and a new receipt schema rather than an implicit best-effort matching heuristic.

A no-op candidate is permitted and receives an explicit, deterministic receipt with zero changed events. This supports a deliberate KeepCurrent strategy without inventing a change.

## Sonata integration

Each Sonata candidate now includes \`patch_receipt: ScorePatchReceiptV1\`. The generator constructs the receipt from the exact baseline Score, candidate Score and the same target index set used by the deterministic transformation. If receipt construction fails, candidate generation returns a typed error; no candidate is silently retained.

The candidate-selection tests independently recompute every receipt and require:
- identical source-score digest across the candidate portfolio;
- identical protected-complement digest across the portfolio;
- every changed event ID to resolve to an index in the declared target;
- exact receipt verification against each candidate Score.

## Tests

The standalone module tests cover:
1. one target pitch edit creates a replayable receipt;
2. a protected-complement change is rejected;
3. insertion/deletion is rejected;
4. score-level metadata change is rejected;
5. empty, duplicate and out-of-range target scopes are rejected;
6. no-op receipts are deterministic and explicitly verifiable;
7. altered receipt fields are rejected;
8. target index lists canonicalize to the same receipt regardless of input ordering.

The Sonata integration additionally verifies every candidate receipt in the actual product path.

## Future work

1. Replace source-index-only identity with an explicit lineage sidecar when the music-theory Score gains stable event IDs.
2. Add typed insertion/deletion/reorder operations with parent/child event links and tombstones.
3. Bind receipts to the exact Sonata plan, obligation ledger, cognitive subintent, model/checkpoint identity, renderer and authorization decision.
4. Add atomic commit/undo receipts to the Studio editor; candidate preview must remain side-effect free.
5. Add multi-region transactions and prove disjoint edits commute, overlapping edits conflict explicitly, and rollback returns the exact source Score digest.
6. Extend the benchmark to measure target edit correctness and protected-complement preservation separately on SMEBench-compatible and rights-cleared real audio cohorts.

## Qualification boundary

A passing test proves the v1 symbolic note-patch receipt behavior on the tested source/target Scores. It does not prove that the musical transformation is valuable, that the audio renderer is perceptually equivalent, that source event identity persists across arbitrary insert/delete/reorder operations, or that any model has artist approval or export rights.


## Stack update

This revision is rebased on the qualified Sonata universal-theory gate. Candidate eligibility uses the music-theory crate's documented universal-invariant policy; style-dependent findings remain present in the full validation report without being treated as cross-style structural corruption.


**Build identity note:** the exact-head workflow explicitly checks out the event SHA; the score-receipt branch and Sonata base both carry the same canonical import for the shared universal-theory gate. The receipt's standalone compilation is therefore tested against the source revision named in the evidence manifest.


## Exact-head test intent

The receipt and Sonata integration gates must run together against the same event SHA and committed lockfile. A standalone receipt unit-test pass is not sufficient: each candidate receipt is independently recomputed inside the Sonata intervention tests before the selected candidate can be accepted.
