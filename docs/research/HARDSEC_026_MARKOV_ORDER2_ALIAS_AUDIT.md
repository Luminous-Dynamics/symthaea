# HARDSEC-026 — First-order Markov sufficiency falsification

**Status:** Exact finite-sequence counterexample and receipt. It demonstrates that matching one-step transition counts does not establish a first-order Markov process. It is not a statistical hypothesis test.

## Exact counterexample

The fixture has two binary sequences:

- control: \`[0,0,0,1,0,1,0,0]\`
- order-two alias: \`[0,0,1,0,0,1,0,0]\`

Both have exactly the same adjacent transition-count matrix:

\[
N=\begin{pmatrix}3&2\\2&0\end{pmatrix}.
\]

Consequently, every fitted first-order empirical transition row is identical across the two sequences. In particular, when the current state is 0, the pooled next-state-1 rate is \(2/5\) in both.

But, conditioned on the previous two states, the next-state rates differ:

| Sequence | \(P(X_{t+1}=1\mid X_t=0,X_{t-1}=0)\) | \(P(X_{t+1}=1\mid X_t=0,X_{t-1}=1)\) |
|---|---:|---:|
| Control | 1/2 | 1/2 |
| Order-two alias | 1 | 0 |

The fixture's deterministic lag-two gap is therefore 0 for the control and 1 for the alias, despite identical first-order transition counts.

This is a constructive identifiability warning: first-order transition counts alone cannot distinguish these sequences. It does not show that an arbitrary finite sequence is generated by a stationary order-two process, and it does not assign a p-value.

## What the auditor does

The Rust example:

1. reads an embedded fixture with a fixed schema;
2. computes adjacent-pair counts and lag-two triplet counts without wraparound;
3. computes exact rational conditional rates;
4. hashes the fixture bytes into the receipt;
5. reports the counterexample with \`statistical_p_value: null\` and \`model_validity_proved: false\`.

The test suite checks the exact matrices and rates. It intentionally does not use "failure to reject" language.

## Integration rule

HARDSEC-025's Markov betting lane must not accept a transition-count-only claim as model qualification. HARDSEC-026 broadens into a preregistered family of held-out diagnostics (lag-2+, hidden-state, regime-switching, state discretizer drift, and adaptive missingness). A diagnostic can falsify a declared model class; a finite collection of non-rejections cannot prove it.

The proper gate has three outcomes:
- \`model_rejected_for_declared_scope\`;
- \`no_misspecification_detected_under_declared_tests\` (still not proof);
- \`inconclusive_insufficient_support\`.

Only the middle outcome may allow a model-scoped experiment to continue, and its receipt must keep \`model_validity_status=not_proved_by_finite_data\`.

## Claim ceiling

This deliverable establishes only an exact finite-sequence counterexample and code conformance for that fixture. It does not establish a statistical test, type-I error, power, Markov validity, hardware measurement quality, physical attack detection, or PMU false-alarm control.
