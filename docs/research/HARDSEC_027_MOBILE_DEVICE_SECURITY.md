# HARDSEC-027 — Mobile hardware security and runtime metrology

**Status:** First privacy-preserving capability-profile contract and synthetic Pixel 8 Pro fixture. No handset has been queried by this PR.

Issue: [HARDSEC-027 / #9736](https://github.com/Luminous-Dynamics/symthaea/issues/9736)

## 1. Why mobile is a separate security research domain

A phone is not a small desktop. Its security state depends on a hardware root of trust, bootloader and rollback state, hardware-backed key services, secure elements/TEEs, memory-safety features, heterogeneous compute, the radio/modem complex, and aggressive power/thermal management. Telemetry access is often less privileged and more vendor-specific than on a development workstation.

The first principle is to distinguish **prevention**, **attestation**, and **runtime detection**:
- prevention mechanisms constrain what the platform can execute or what memory/key operations are permitted;
- attestation provides evidence about a particular device and boot/key state;
- runtime detection looks for residual suspicious behavior and must qualify its own sensors.

A behavioral classifier cannot replace a secure boot chain, StrongBox, or memory tagging. Conversely, a secure boot attestation does not prove that the device remains uncompromised at runtime or that a PMU observation is unbiased.

## 2. Platform facts that shape the benchmark

### Android

Android KeyMint/Keymaster attestation distinguishes \`Software\`, \`TrustedEnvironment\`, and \`StrongBox\` security levels. The attestation structure contains separate software- and hardware-enforced authorization lists, a challenge, and a RootOfTrust including bootloader lock state and Verified Boot state. The hardware-enforced list is generated by the TEE or StrongBox rather than by ordinary Android platform code. See the [Android Key and ID Attestation documentation](https://source.android.com/docs/security/features/keystore/attestation).

The Android Compatibility Definition Document's StrongBox requirements specify a discrete CPU sharing no cache, DRAM, coprocessors, or other core resources with the application processor, plus protections for tampering and power/timing/electromagnetic/thermal side channels. Those are platform conformance requirements; our profile must still verify what the current device actually attests. See [CDD section 9.11.2](https://android.googlesource.com/platform/compatibility/cdd/+/e2fee2f/9_security-model/9_11_keys-and-credentials.md).

The [Android MTE developer guide](https://developer.android.com/ndk/guides/arm-mte) lists Pixel 8 Pro (Husky) among devices supporting MTE. It explains that runtime status should be checked on-device; model support is not equivalent to a particular build's current enablement or mode. AOSP also distinguishes synchronous and asynchronous behavior: synchronous mode traps immediately on tag mismatch, while asynchronous mode may continue until a later kernel entry. See [AOSP MTE documentation](https://source.android.com/docs/security/test/memory-safety/arm-mte).

Google's [Pixel security certifications](https://support.google.com/pixelphone/answer/11062200) list Tensor G3 and Titan M2 security-component certifications for the Pixel 8 Pro family, alongside Tensor security core and Trusty TEE platform descriptions. The fixture records these as vendor-documented model capabilities only; no attestation or runtime configuration is inferred.

Simpleperf's AOSP description says it reads Linux perf events through \`perf_event_open\`, including PMU counters for cycles, instructions, and cache misses. That does not mean a third-party app can access every event: the actual device policy, privilege context, event set, counter scheduling and multiplexing must be measured. See [AOSP Simpleperf introduction](https://android.googlesource.com/platform/prebuilts/simpleperf/+/557578b22806b54739e6426ed760bec9976aca05/README.md).

Android thermal services expose a severity status to apps, while detailed thermal sensor/event information is restricted to trusted system services. Battery and thermal constraints can alter sustained performance. Therefore, PMU/latency measurements must be stratified by thermal and power states instead of treating them as stationary noise. See [Android thermal mitigation](https://source.android.com/docs/core/power/thermal-mitigation).

### Apple

Apple's September 2025 Memory Integrity Enforcement (MIE) description says the iPhone 17 family and iPhone Air use hardware/software integration built around Enhanced Memory Tagging Extension, secure allocators, and tag-confidentiality protections. Apple reports coverage for key attack surfaces including the kernel and more than 70 userland processes. These are Apple's published descriptions and should be treated as a platform-prevention reference, not a direct detector-accuracy comparator. See [Apple Security Research: MIE](https://security.apple.com/blog/memory-integrity-enforcement).

For a first project, Android is the practical acquisition target because the user has a Pixel 8 Pro and Android publishes developer-facing MTE and Simpleperf tooling. An Apple MIE device should remain a separate reference lane unless a legitimate research device and measurement method are available. Do not infer Apple's internal MIE status from a model string alone.

### Adjacent mobile attack-surface research

- A 2024 IEEE Transactions on Dependable and Secure Computing study demonstrated cross-app side channels from Android sensor multiplexing, including spectral covert channels and coarse app profiling using standard mobile services. This justifies treating sensor-hub scheduling as a first-class measurement and privacy surface, not merely reading CPU counters. See [Shepherd et al., DOI 10.1109/TDSC.2023.3323732](https://doi.org/10.1109/TDSC.2023.3323732).
- USENIX Security 2025 research analysed kernel drivers reachable by untrusted apps across 131 Android devices and reported attack surface beyond GPU drivers. This motivates device-family and vendor-driver holdouts, not a single Pixel-only evaluation. See [The Doom of Device Drivers](https://www.usenix.org/conference/usenixsecurity25/presentation/maar-doom).
- The USENIX WOOT 2026 *SoK: Insecurity of Cellular Basebands* systematizes baseband vulnerability research and emphasizes the complexity and proprietary nature of cellular baseband implementations. This makes the modem a distinct evidence boundary: Android app/kernel telemetry cannot be assumed to observe or attest its internal state. See [Carnot & Francillon, WOOT 2026](https://www.usenix.org/conference/woot26/presentation/carnot).

## 3. First implementation slice

The PR adds:
- \`schemas/hardsec-mobile-device-profile-v1.schema.json\`;
- \`tests/fixtures/hardsec/mobile-device-v1/pixel-8-pro-capability-fixture.json\`;
- \`examples/hardsec_mobile_device_profile_audit.rs\`;
- opt-in Cargo feature \`hardsec-mobile-device-profile-audit\`.

The profile explicitly separates:
- vendor-documented hardware support;
- on-device runtime enablement and mode;
- cryptographically verified attestation;
- PMU access and acquisition quality;
- environment (thermal, power, charging, radio activity, screen);
- evidence provenance and claim ceilings.

The sample is a **synthetic fixture**, not a dump from the user's handset. It includes no IMEI, serial number, unique hardware identifier, location, raw attestation certificate, or user data. MTE is marked \`vendor_documented\` for product-family support but \`not_measured\` for runtime state. Boot/attestation and PMU acquisition are also \`not_measured\`.

The Rust auditor rejects sensitive identifier fields recursively. It refuses to promote a vendor-documentation statement into verified runtime enablement, a trusted attestation chain, or qualified PMU measurement. Boot-integrity, PMU, and protection claims are linked to explicit evidence IDs. The auditor resolves those IDs against the evidence ledger and checks the source type for that specific claim, so an unrelated attestation or lab receipt cannot qualify another subsystem.

## 4. Mobile threat model and research lanes

1. **Boot integrity and rollback:** locked/unlocked bootloader, Verified Boot state, rollback protection, partition patch-level binding, recovery flows and update transitions.
2. **Hardware-backed identity and key control:** KeyMint/TEE/StrongBox security level, attestation challenge freshness, certificate-chain verification and revocation, hardware-enforced key policy, privacy-preserving identifiers.
3. **Memory safety and control-flow protection:** MTE/EMTE modes and protected process scope, PAC, BTI/CFI, allocator hardening, kernel and privileged-process coverage.
4. **Shared-resource and side-channel behavior:** PMU/cache, DVFS, thermal, power, DRAM, GPU/NPU, sensor hub, cellular modem, Wi-Fi/Bluetooth/NFC coexistence.
5. **Physical and near-physical assurance:** non-destructive fault/voltage/clock/thermal observation, debug-interface configuration, secure-element isolation and published lab methods. No destructive or unauthorized testing.
6. **Privacy and user-state safety:** stolen/locked/unlocked transitions, local-only telemetry, minimal retention, explicit sensor admission and fail-closed handling.

## 5. Benchmark design

### Device strata

- Pixel 8 Pro / Tensor G3 (first acquisition candidate).
- At least one Qualcomm Snapdragon Android device.
- At least one other SoC family (Exynos or MediaTek).
- An iPhone with MIE support as a separate prevention-reference lane, only if a legitimate research device and safe measurement path are available.

The initial target is three Android devices across multiple SoC families, then iOS as a separate platform. Each device needs exact build, vendor/boot patch levels, bootloader state, and attested security level recorded at capture time.

### Controlled factors

Cold/warm thermal state; charging/discharging; battery saver/performance mode; CPU cluster; low/medium/high contention; radio idle/active (coarse category only); screen on/off/doze; PMU event set; sampling rate; collection privilege; MTE mode; and OS/vendor patch level.

### Comparators

Platform defenses (Verified Boot, KeyMint/StrongBox, MTE/MIE, PAC/BTI, SELinux); no-monitor and minimal-observer controls; Simpleperf/PMU features only after metrology qualification; statistical CUSUM/GLR and Page–Hinkley/EWMA; DT/RF/SVM; and Symthaea HDC/CfC selective cascades.

### Metrics and initial targets

Targets below are aspirational and require pre-registration:
- zero clean verdicts for invalid, stale, replayed, unverifiable attestation or untrusted boot state;
- zero unsupported/missing PMU events converted to zero-valued observations;
- measurement deviation and observer effect qualified per event, device, CPU cluster and thermal stratum;
- initial incremental budget: ≤1% median CPU time and ≤1% additional battery per 24-hour run; publish p95 and worst strata;
- ≤0.1 false alerts/device-day at a validation-frozen operating point;
- ≥95% pooled attack-effect recall and ≥90% worst-family recall, without relaxing the false-alert budget;
- p95 detection delay ≤2 valid observation windows;
- 100% receipt coverage of boot state, patch levels, acquisition status and abstention reasons;
- zero raw user data or stable hardware identifiers in exported receipts.

Do not claim these targets are achieved. Do not combine prevention effectiveness with classifier recall into one score.

## 6. Research paradigm shifts

**Attestation-bound measurement.** Bind a run to a fresh, challenge-bound device-state evidence receipt. Use privacy-preserving pseudonymous run IDs; never export stable device identifiers or raw certificates.

**Sensor self-qualification.** A mobile detector should emit a sensor-quality state (qualified / degraded / unavailable) alongside every decision. Multiplexed, throttled, stale, permission-denied, or missing observations cannot be treated as benign.

**Protection-aware detection.** Evaluate only the residual attack surface after the platform's prevention controls are known. Test whether the monitor adds useful coverage beyond hardware defenses, not whether it can outscore those defenses on an unrelated classifier benchmark.

**Energy-aware selective monitoring.** Use a low-cost passive mode during stable periods, escalate only on a predeclared risk/evidence trigger, and abstain when the acquisition budget or sensor quality fails. Measure energy and thermal feedback as part of the algorithm, not just deployment overhead.

**Cross-platform honesty.** Android and iOS do not expose identical telemetry or attestation. Compare common outcome measures and capability envelopes; do not normalize away differences in privilege, silicon or vendor instrumentation.

## 7. Claim ceiling

This phase establishes only profile shape, privacy contract and source/evidence distinctions. It does not establish the user's device configuration, runtime MTE enablement, attestation result, PMU access, observer effect, physical attack resistance, or detection performance. The synthetic fixture must remain visibly synthetic until replaced by a privacy-reviewed, locally captured device receipt.
