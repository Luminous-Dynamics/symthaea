# GameBench Environment Event Authentication v0.1

**Status:** research/implementation design; not an implemented verifier or qualification result  
**Date:** 2026-11-28  
**Parent:** GameBench #14137; causal twins #14216; transition adapter #14259  
**Depends on:** transition bridge `research/symthaea-gamebench-transition-bridge-v0-1/`

## 1. Objective

Close the gap between a structurally valid transition record and an authenticated account of what the environment actually did.

The transition bridge currently checks identities, timing, side-effect class, observation-digest continuity, outcome vocabulary, replay identifiers, and cost ceilings. It deliberately does not establish that the supplied event or trace digests were generated by the trusted environment. A non-empty digest is a commitment-shaped string, not proof of origin or correctness.

This slice specifies the minimum trusted path from a real environment transition to a verifier-approved domain receipt. It does not assume that the existing F6 environment has a particular API or file layout; the adapter must be written against the actual source after repository inspection.

## 2. Trust boundaries

Use three separately permissioned roles:

1. **Environment executor** owns mutable world state and is the only process allowed to apply interventions. It emits an append-only event stream from the actual transition path.
2. **Candidate** receives only public observations, legal actions, permitted intervention affordances, and public outcomes. It never receives hidden mechanism labels, evaluator loss tables, signing keys, or evaluator world IDs.
3. **Evaluator/verifier** owns challenge truth, compatible-world support, terminal loss, and scoring. It verifies event provenance and replay before passing a validated transition to the domain adapter.

Rust module privacy and filtered structs are not process isolation. Confirmatory runs must use an OS/process boundary or an equivalent capability boundary, with evaluator secrets unavailable to the candidate process.

## 3. Canonical event envelope

Define a versioned, deterministic envelope. At minimum it binds:

- protocol/schema version and hash algorithm identifier;
- run, episode, monotonically increasing event sequence, invocation, intervention, and action identifiers;
- prior event hash (genesis is explicit);
- issued, applied, and observed logical steps, plus wall-clock timestamps only where the environment has a trusted clock contract;
- side-effect class and declared preconditions;
- pre-state and post-state observation digests;
- public outcome identifier and outcome-payload digest;
- actual resource-cost vector, units, and accounting source;
- environment build/source identity and deterministic seed commitment;
- transition-trace digest and executor identity.

Canonicalization requirements:

- fixed field ordering and explicit integer/string encodings;
- explicit distinction between absent, null, and empty values;
- reject NaN and infinities in numeric fields; use integer/fixed-point units for costs;
- domain-separate hashes by protocol version and record type;
- hash the canonical bytes, not a debug string or ordinary JSON serialization;
- pin canonicalization test vectors and publish cross-implementation fixtures.

A digest chain detects deletion, insertion, and reordering relative to a trusted checkpoint, but does not alone authenticate the producer. Bind each event hash to a signature from a run-scoped executor key, or use an equivalent trusted local attestation mechanism. Key provisioning, rotation, revocation, and run binding must be explicit. Never put the signing key in the candidate process.

## 4. State-transition verification

The verifier should perform checks in this order:

1. Parse and validate schema/version; reject unknown critical fields and unsupported versions.
2. Verify executor identity and signature against the run's authorized key.
3. Verify the event hash from canonical bytes and the previous-event hash link.
4. Verify contiguous sequence number and episode/run identity.
5. Verify invocation uniqueness and exact action/intervention binding to the issued contract.
6. Verify pre-state digest equals the verifier's last accepted observation digest.
7. Independently replay the action against the authoritative environment snapshot/trace when deterministic replay is available.
8. Compare replayed post-state and outcome with the event's post-state and public outcome.
9. Verify side-effect class, preconditions, logical timing/deadline, and declared outcome vocabulary.
10. Reconcile the resource-cost vector against executor counters and remaining budget.
11. Only then pass a typed verified-event value to `validate_and_apply_transition`.

The adapter must not be callable with an unverified raw event in the confirmatory path. Prefer a distinct `VerifiedEnvironmentTransition` type whose constructor is private to the verifier module/crate. If the verifier and adapter remain in one process, document that this is a type-level guard, not a security boundary.

## 5. Failure semantics: fail closed, then reconcile

Distinguish:
- **Rejected before execution:** contract or authorization failed; no world mutation is permitted.
- **Executed and verified:** transition accepted and costs charged.
- **Execution outcome unknown:** timeout, process loss, partial trace, or verifier outage after a mutation may have occurred. Freeze further mutation for the episode; query/replay the authoritative environment and reconcile before resuming.
- **Executed but unverifiable:** preserve raw signed evidence and mark the episode unqualified. Never convert missing evidence into a no-op or a successful transition.

Never retry a mutating invocation with a new identifier merely because the caller timed out. Idempotency keys and executor-side invocation deduplication must ensure exactly-once application or explicit unknown-outcome reconciliation.

## 6. Required adversarial and metamorphic tests

### Canonicalization and cryptographic binding
- fixed cross-language canonicalization vectors;
- field-order invariance only where the schema declares it;
- mutation of every bound field invalidates the signature/hash;
- wrong key, revoked key, wrong run key, wrong protocol domain, and altered prior hash reject;
- truncated, duplicated, reordered, and spliced event streams reject.

### State and replay
- wrong pre-state, forged post-state, wrong outcome, wrong action, and wrong intervention reject;
- deterministic replay mismatch rejects;
- duplicate invocation and duplicate sequence reject;
- stale, early, late, and out-of-order observations reject;
- unknown side-effect class and undeclared outcome reject.

### Accounting and uncertainty
- each resource-cost component is charged exactly once;
- unit mismatch, overflow, negative cost, NaN, infinity, and budget overrun reject;
- executor crash before mutation, during mutation, and after mutation but before acknowledgement enter distinct tested states;
- timeout followed by retry cannot double-apply;
- missing evidence yields unknown/unqualified, never success.

### Isolation and leakage
- candidate cannot read evaluator manifest, signing key, hidden world ID, loss table, or raw private trace;
- candidate-visible event projection is invariant under evaluator-only field changes;
- challenge seeds and sealed answer keys are unavailable before run closure.

Use mutation testing on the verifier itself: deliberately remove or invert each guard and prove the negative-control suite catches it. A passing test suite without grader-mutation sensitivity is not sufficient evidence of verifier strength.

## 7. Integration sequence

1. Inspect the actual `HiddenMechanicsGame` implementation and identify the single authoritative state-mutation path. Do not infer a path from naming or duplicate the game transition logic.
2. Add an environment-owned event emission point immediately around the real state transition; capture pre/post observation from the environment, not the candidate.
3. Define canonical event bytes and deterministic test vectors.
4. Add a run-scoped executor identity and verifier; keep signing material outside candidate-visible APIs.
5. Add a replay adapter using the existing authoritative transition function, not a second simulator.
6. Adapt verified events into the existing domain transition record; preserve #10314 as the canonical run ledger.
7. Add negative-control and grader-mutation tests before any candidate campaign.
8. Run the frozen fixture suite and compare receipts across independent replays.

If deterministic replay is impossible for a particular environment component, label that evidence tier explicitly (signed event only, not replay-verified) and exclude it from the strongest qualification claim.

## 8. Evidence tiers

| Tier | Evidence | Permitted claim |
|---|---|---|
| E0 | Candidate-authored/self-reported transition | Diagnostic only |
| E1 | Structurally valid event from environment adapter | Protocol consistency only |
| E2 | Canonical hash chain + authorized executor signature | Origin/integrity under stated key assumptions |
| E3 | E2 + independent deterministic replay agreement | Reproduced transition under pinned environment build |
| E4 | E3 + isolated evaluator, sealed truth, mutation-tested grader, canonical run receipt | Confirmatory benchmark evidence |

Do not collapse these tiers into one boolean `verified` flag. Record the exact evidence tier and its assumptions on every receipt.

## 9. Qualification gates

Proposed gates, not achieved results:

- 100% canonicalization test-vector agreement across two independent implementations;
- 0 accepted altered, replayed, spliced, stale, or unauthorized events in the frozen negative-control suite;
- 100% replay agreement on deterministic fixtures;
- 0 double-applied interventions under injected timeout/crash schedules;
- 0 candidate-visible evaluator-secret disclosures in the isolation test suite;
- 100% resource-cost reconciliation on frozen fixtures;
- mutation score reported for every verifier guard, with no untested critical guard;
- exact source/build/seed/schema identities attached to each run receipt.

A passing protocol test does not prove the simulator models the real world or that a physical intervention is safe. Those require separate environment-fidelity and domain-safety evidence.

## 10. Benchmark extensions enabled by authenticated transitions

Once the event path is trustworthy, add the following task families without changing the adapter into a planner:

- **Irreversibility frontier:** compare reversible information probes with irreversible interventions; score decision improvement against irreversible side-effect exposure.
- **Delayed causal effects:** separate immediate observation from delayed consequences; test whether the candidate waits, forecasts, and revises.
- **Intervention interference:** interventions alter the usefulness or safety of later interventions; test sequence-aware planning against greedy one-step selection.
- **Resource-vector constraints:** model time, energy, inventory, risk, and opportunity cost separately rather than collapsing them into an arbitrary scalar.
- **Partial observability with endogenous sensors:** actions can change what becomes observable; score both information and observation-channel damage.
- **Unknown mechanism introduction:** inject an unannounced mechanism mid-episode; score detection, containment, and safe recovery rather than forced classification.

These should be separate benchmark tracks with their own contracts and denominators, not silently mixed into v0.1 results.

## 11. Claim boundary

This document is a design specification. It adds no executable verifier, environment adapter, cryptographic implementation, test result, benchmark score, or safety certification. The exact F6 source path and API must be inspected before implementation. All proposed gates remain unqualified until run against exact source heads with reproducible receipts.
