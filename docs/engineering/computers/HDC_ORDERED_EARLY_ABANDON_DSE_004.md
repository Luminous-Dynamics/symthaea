# HDC-ORDERED-EARLY-ABANDON-DSE-004 — data-dependent chunk order for exact retrieval

Status: benchmark and independent mathematical reference pilot authored; Rust compilation and Criterion timing have not been performed in this environment.

## Hypothesis

Exact Hamming distance is the sum of non-negative per-chunk mismatch counts. The order in which chunks are visited does not change the final exact distance, but it can change how early a worse candidate is rejected by a monotone partial-distance bound.

The canonical BinaryHV has 16,384 bits = 2,048 bytes. This experiment partitions it into thirty-two 64-byte chunks and compares:

1. Exact full Hamming scan (runtime-dispatched SIMD baseline).
2. Sequential chunk early-abandonment.
3. Corpus-variability-ranked chunk early-abandonment.

The ranked order is computed once from the corpus. For every bit position inside each chunk, the builder counts the number of candidate vectors with that bit set and accumulates `min(ones, zeros)`. This estimates how often candidates differ at those positions, without depending on a query's true winner or any candidate identity. Chunks with larger aggregate variation are inspected first.

No candidate-specific sidecar is added: the index is one 32-entry chunk order. The trade-off is that chunk scoring must inspect the corpus, and the query kernel uses explicit 64-byte scalar count_ones loops rather than the existing optimized SIMD Hamming call. The benchmark therefore must show a *measured end-to-end benefit* before anyone replaces the SIMD baseline.

## New benchmark

File: `crates/core/symthaea-core/benches/hdc_ordered_early_abandon.rs`

Run on an exact source revision:

    cargo bench -p symthaea-core --bench hdc_ordered_early_abandon

Axes:
- corpus sizes 256, 1,024, 4,096 and 16,384;
- random corpus/control query (asserted not equal to any corpus candidate);
- localized-tail workload in which all candidate variation is restricted to the last 512 bytes;
- flat exact SIMD, sequential chunk early-abandon and corpus-variability-ranked early-abandon;
- separately timed chunk-order construction.

The localized-tail workload is intentional: sequential order scans 1,536 invariant bytes before reaching variable blocks. It tests whether a cheap corpus-only ordering can move discriminative blocks forward. It does not claim that real Symthaea HDC corpora have this structure. Random data is the required negative control.

The timed byte-visit diagnostic is outside timed Criterion iterations and reports logical bytes examined by the algorithm. It is not a hardware cache-miss counter, physical memory-byte count, timing measurement, or energy result. Index-building cost must be amortized against a declared number of queries before describing a win.

## Exactness argument

For a fixed query and candidate, each chunk contributes a non-negative integer mismatch count. Therefore, after processing any subset of chunks, the partial sum is a lower bound on the complete distance. Candidates are evaluated in increasing candidate-ID order. Once a later candidate's partial sum is greater than or equal to the incumbent's complete distance, no remaining chunk can lower that sum; it cannot beat the incumbent and cannot win an equal-distance tie because its ID is larger.

All variants are checked against exhaustive exact Hamming top-1 before timing. Duplicate exact winners test deterministic lowest-ID tie behavior. The algorithm is not approximate.

## Independent model pilot (not Rust execution)

A separate Python bit-vector model used 512 16,384-bit candidates per profile and the same 32 × 64-byte chunking and variability score. Both reordered paths matched exhaustive top-1 ID and distance.

| Profile | Exact winner distance | Sequential bytes visited | Variability-ranked bytes visited |
|---|---:|---:|---:|
| Random control | 8,025 bits | 99.77% of corpus payload | 99.79% |
| Localized tail | 24 bits | 80.14% | 3.31% |

This is logical traversal accounting on an independent model, not elapsed time or physical traffic. On the random control the heuristic did not help; it was fractionally worse. On the localized-tail fixture, ranking blocks by variation reduced logical byte visits substantially because it checks informative blocks before invariant ones. It is still possible for the ranked algorithm to lose in wall-clock time because it uses scalar loops, branch checks, and an allocated block order while the flat implementation can use SIMD. The code must be measured on actual hardware.

The Rust implementation uses the repository's BLAKE3-based deterministic vector generator, while the independent model uses NumPy-generated bytes. The pilot validates the bound and the workload hypothesis, not equality of generated fixtures or Rust source correctness.

## Go/no-go and industry comparison

1. Exact winner ID and distance must match the flat oracle on every fixture.
2. The random control must not regress materially versus the current SIMD implementation.
3. Compare kernel-only runtime and setup-inclusive amortized runtime separately.
4. Keep the corpus order only if query-latency improvement exceeds index-build and per-query overhead over the declared number of queries.
5. For an industry comparison, match the same BinaryHV bytes and exact top-1 semantics against FAISS `IndexBinaryFlat`; do not compare only bytes-visited or mathematical operation counts.
6. Use measured latency distribution and hardware performance counters where available; measure energy with calibrated equipment and a declared system boundary.

FAISS binary index guide: https://github.com/facebookresearch/faiss/wiki/Binary-Indexes

MLPerf Tiny's matched-workload, quality-target and calibrated-energy discipline is relevant to later edge-device comparisons: https://mlcommons.org/benchmarks/inference-tiny/

This is an experiment, not a performance or SOTA claim.
