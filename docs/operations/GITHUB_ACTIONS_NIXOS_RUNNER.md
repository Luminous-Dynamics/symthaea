# Symthaea Trusted CPU GitHub Actions Runner

## Purpose

This runner is an execution-capacity fallback for trusted correctness validation when GitHub-hosted assignment latency becomes operationally unacceptable.

It is infrastructure only. Running a workflow here does not change an experimental result, weaken a scientific gate, or turn an unexecuted workflow into evidence.

The first-party fallback is intentionally CPU-only. GPU access is a separate capability and security design because exposing host devices weakens the default NixOS GitHub-runner isolation boundary.

## Current v2 security model

Symthaea is public, so the runner must never become a generic `self-hosted` execution target for arbitrary branch or fork code.

The v2 defense is layered:

1. repository-scoped ephemeral GitHub runner;
2. GitHub default labels disabled;
3. one unique capability label: `symthaea-trusted-cpu-v1`;
4. only explicitly reviewed manual/main-only/tokenless workflows may request that label;
5. protected `main` is required by issue #330;
6. the trusted host is additionally pinned to one exact reviewed `main` commit through `trustedHarnessCommit`;
7. a host-owned pre-job hook rejects any assigned job whose server-provided identity does not match that pin and the fixed workflow allowlist;
8. unmerged recovery targets are separately frozen by exact commit/tree/base/path/dependency identities;
9. the runner-registration credential is validated before bootstrap and remains inaccessible to workflow code;
10. the host is disposable, CPU-only, and isolated from sensitive LAN/control-plane services.

No single layer substitutes for the others.

## Host-facing module API

`nix/modules/github-actions-runner.nix` intentionally exposes only four host options:

- `enable`
- `name`
- `tokenFile`
- `trustedHarnessCommit`

Everything else relevant to scheduling and lifecycle is fixed in the module:

- repository: `https://github.com/Luminous-Dynamics/symthaea`;
- repository ID: `1136141775` in the host admission policy;
- token mode: access token;
- lifecycle: ephemeral;
- replacement registration: enabled;
- runner self-update: disabled by pinned nixpkgs;
- GitHub default labels: disabled;
- custom capability: `symthaea-trusted-cpu-v1`;
- JavaScript runtime: Node 24 only;
- Symthaea-specific ambient packages: none;
- GPU routing: unavailable.

Because default labels are disabled, the host does not advertise generic `self-hosted`, OS, architecture, or `gpu` labels.

## Trusted-root prerequisite

The runner must not be activated while the repository harness root is directly mutable.

Issue #330 is an activation blocker. Before enabling `symthaea-trusted-cpu-v1`, verify from GitHub that `main` has effective branch protection or a repository ruleset that prevents ordinary direct/force-push mutation outside the reviewed promotion path.

The host-side pre-job hook additionally requires `GITHUB_REF_PROTECTED == true`.

A main-only workflow is not itself a trust boundary when `main` is unprotected.

## Exact host harness pin

Server-side protection is supplemented by a host-local immutable pin.

`trustedHarnessCommit` is the exact reviewed protected-main commit allowed to schedule work onto the trusted CPU capability.

Example:

```nix
services.symthaea-ci-runner = {
  enable = true;
  tokenFile = "/run/secrets/github-runner/symthaea-pat";
  trustedHarnessCommit = "0123456789abcdef0123456789abcdef01234567";
};
```

The pin must be an exact lowercase 40-hex Git commit.

Any later `main` commit is rejected until the operator deliberately reviews the new harness, updates `trustedHarnessCommit`, rebuilds the host, and reruns the trusted smoke. Do not automatically follow `origin/main` or populate this option from workflow input.

See `TRUSTED_RUNNER_JOB_ADMISSION.md` for the exact admission contract and repinning lifecycle.

## Host-side pre-job admission

The runner service sets `ACTIONS_RUNNER_HOOK_JOB_STARTED` to a Nix-store-pinned script generated by the host configuration.

GitHub invokes this hook after assigning the job but before workflow-defined steps. A non-zero exit fails the job.

The v2 hook requires all of the following:

- exact repository name and repository ID;
- `https://github.com` server;
- `workflow_dispatch` event;
- `refs/heads/main` branch;
- GitHub reports that ref protected;
- `GITHUB_SHA == trustedHarnessCommit`;
- `GITHUB_WORKFLOW_SHA == trustedHarnessCommit`;
- `GITHUB_WORKFLOW_REF` is exactly one of the four reviewed trusted workflows.

The four allowed workflow refs are:

- `self-hosted-runner-smoke.yml`;
- `self-hosted-ai-assurance-foundation-recovery.yml`;
- `self-hosted-ai-assurance-budget-recovery.yml`;
- `self-hosted-sym-arch-002a-core-recovery.yml`;

all from `refs/heads/main` in `Luminous-Dynamics/symthaea`.

This hook is defense in depth. It does **not** replace #330 server-side protection.

## Host isolation

Treat the runner as a disposable build appliance, not a workstation.

Prefer a dedicated VM or host with:

- no personal files or browser/session state;
- no SSH agent, developer keys, cloud credentials, or mounted home directories;
- no writable mounts from production systems;
- no privileged Docker socket or equivalent host-control API;
- a network segment that exposes no sensitive LAN/control-plane services;
- only the external runner-registration credential required by the service.

The NixOS systemd sandbox protects local filesystem/process boundaries, but target compilation/tests still need outbound GitHub/Nix/Cargo access. Network placement is therefore part of the threat model.

## Runner-registration credential

Never place a GitHub token, registration token, private key, or other credential in this repository, a Nix expression, a flake input, Actions variables, logs, or shell history.

For the v2 emergency/static-secret design, `tokenFile` must point to an external runtime file outside the Nix store. Use a fine-grained PAT restricted to `Luminous-Dynamics/symthaea` with only the repository permission required to manage the repository runner-registration lifecycle.

Before the upstream privileged bootstrap reads the token, the Symthaea module fails closed unless the file is:

- a regular file;
- owned by UID 0;
- mode exactly `0400` or `0600`;
- non-empty;
- at most 4096 bytes;
- one printable non-whitespace token;
- free of newlines/control bytes.

The checker must not print or hash the credential value.

The original external token path and the upstream persistent comparison copy are inaccessible to the workflow job process after bootstrap under the pinned nixpkgs lifecycle.

Issue #322 tracks the stronger v3 direction: keep the GitHub App private key in a separate root-owned broker and mint short-lived repository-specific installation authority only when runner registration requires it. v2 deliberately remains the simpler PAT-backed emergency fallback until qualified.

## Minimal validation shell

Do not reproduce `ubuntu-latest` by downloading unmanaged Rust binaries or enabling broad compatibility layers on this host.

`nix/ci-rust-shell.nix` provides the purpose-built validation environment from pinned flake inputs. It contains the tools required by the trusted CPU path, including:

- the `rust-toolchain.toml` Rust toolchain;
- rustfmt;
- Clippy;
- CA certificates;
- compiler/linker support;
- OpenSSL + headers;
- pkg-config.

The current repository pin is Rust `1.96.0`.

The ambient runner service adds zero Symthaea-specific packages.

## Eval policy

`nix/tests/eval-github-actions-runner.nix` evaluates the runner without contacting GitHub or reading a real token.

It is expected to prove at least:

- repository scope and fixed ephemeral/access-token mode;
- no default GitHub labels;
- exact custom capability label;
- fixed Node runtime and no extra Symthaea packages;
- exact four-option public module API;
- external secret-path type restrictions;
- blank runner-name rejection;
- missing/malformed trusted-harness pin rejection;
- pinned upstream systemd hardening;
- root-only credential-preflight ordering and policy;
- credential-value non-disclosure regression;
- installation of the host-side `ACTIONS_RUNNER_HOOK_JOB_STARTED` gate;
- exact repository/protected-main/manual-event/harness-SHA/workflow allowlist in that gate;
- restricted address families without raw packet sockets;
- runner self-update remains disabled.

The trusted routing eval separately proves only the reviewed workflows can request `symthaea-trusted-cpu-v1` and that those workflows remain manual, tokenless, and main-only.

## Trusted smoke

`.github/workflows/self-hosted-runner-smoke.yml` is `workflow_dispatch` only and main-only.

Before smoke dispatch:

1. satisfy #330;
2. identify the exact reviewed protected-main commit;
3. set that commit as `trustedHarnessCommit` in host configuration;
4. rebuild/switch the host;
5. verify the runner is online with exactly the trusted capability label.

The host admission hook should allow the smoke only when GitHub's job/workflow SHAs equal that deployed pin.

The smoke then:

1. fetches the exact protected-main `GITHUB_SHA` without relying on a broad checkout token;
2. verifies detached `HEAD == GITHUB_SHA`;
3. records source/Nix/Rust provenance;
4. evaluates runner and routing policy;
5. places Cargo state under `RUNNER_TEMP`;
6. enters the pinned validation shell and verifies Rust/Cargo/rustfmt/Clippy;
7. runs a locked CPU smoke check;
8. verifies the source tree remained immutable.

Do not add a pull-request trigger to this capability.

## Frozen unmerged recovery targets

Each recovery target has a separate manually dispatched trusted workflow with no ref/SHA inputs.

The workflow itself fixes the target commit/tree/base and exact path allowlist before target code can execute.

For #186, the recovery additionally fixes:

- target commit `251c47c5a1f09015ab6c29794df7ac5b6efae373`;
- target tree `1451a57e2dcaf50de6b5b43776364a5af8b78f15`;
- lower base `6ca61356c6ff49b2ba77cae332f006d054d5f84d`;
- hosted AI Assurance workflow blob `35bbddd9d6a7f8ad77073e4ab4faf6722f00deea`;
- target `Cargo.lock` blob `e70e88105e2774dc9c6384fbd86d33a2d0ca8af7`;
- base `Cargo.lock` blob `1d5b6c3dffb474fabef0f8237c6741b4f252bc62`;
- exact changed paths;
- exact lockfile delta shape.

The #186 lock delta only adds the workspace `symthaea-ai-assurance` package stanza; it does not alter third-party package versions/checksums/sources/transitive selection.

A recovery PASS is correctness/reproducibility evidence for that exact frozen tree on the recorded trusted substrate. It is not hosted-runner equivalence, full repository CI, performance evidence, or qualification of later stacked PRs.

## GPU runners are separate

Do not reuse this capability for GPU workloads.

Access to `/dev/nvidia*`, render devices, CUDA state, or other accelerator resources changes the host threat model and requires a distinct capability label and security design.

## Performance boundary

The trusted CPU fallback is initially a correctness substrate: formatting, deterministic tests, compile checks, schema checks, and similar gates.

Do not treat its timing, throughput, RSS, or other performance measurements as interchangeable with GitHub-hosted results. Any claim-bearing measurement on this substrate needs its own runtime-context binding.

## Activation checklist

The trusted CPU fallback is operational only when **all** of the following hold:

- #330 is satisfied and GitHub readback proves protected `main`;
- ordinary direct/force pushes cannot silently rewrite the trusted harness;
- host config pins an exact reviewed protected-main SHA in `trustedHarnessCommit`;
- missing/malformed pins fail Nix assertions;
- the host-side hook rejects unprotected, stale-SHA, wrong-event, wrong-repository, and unreviewed-workflow jobs before workflow steps;
- runner and routing Nix eval tests pass against pinned nixpkgs;
- the PAT is repository-scoped/minimal and its external runtime file satisfies the enforced root/mode/content policy;
- the runner service is healthy after reboot;
- GitHub reports the runner online with exactly `symthaea-trusted-cpu-v1`;
- the isolated host contains no unrelated secrets or host-control sockets;
- its network segment exposes no sensitive LAN/control-plane services;
- the main-only smoke passes from the exact deployed harness commit;
- source/harness trees remain immutable during smoke;
- locked dependency resolution is accepted;
- the runner remains ephemeral and self-update-disabled;
- no generic/fork/untrusted/GPU workflow can match the trusted CPU capability;
- disabling the module removes the host from active capacity without changing scientific evidence.

## Qualification status

Until the Nix eval and real protected-main smoke execute successfully, the v2 branch is **statically reviewed infrastructure**, not qualified trusted-runner capacity.

Runner substrate is operational provenance, not experimental outcome. #186/#196 and later assurance work still require their own exact-tree qualification evidence regardless of where the gate executes.
