# Persistent Human-AI Team Trajectories and Collective Intelligence

**Status:** research extension proposal, 15 November 2026  
**Implementation status:** trajectory receipt model, validator, schema, CLI command, and tests authored; service orchestration and longitudinal studies remain future work.

## 1. The unit-of-analysis shift

A sequence of successful conversations does not automatically constitute a persistent team. A team-level claim requires identifiable contributors, interdependent activity, defined roles and authority, continuity across cycles, and a record of how prior collective activity affects later participation.

The October 2026 OHAI framework makes three analytical objects distinct:

1. **System configuration:** which humans and agents participate, model snapshots, prompts, tools, memory, roles, authority, procedures, and infrastructure.
2. **Collective functioning:** how distributed contributions are actually coordinated, combined, handed off, challenged, and used.
3. **Collective intelligence:** a general group-level capacity that manifests across a specified universe of diverse tasks.

A component capability does not establish team functioning, and a single task score does not establish collective intelligence. The framework proposes a staged empirical programme beginning with configuration/measurement qualification, then local relations, longitudinal team-level phenomena, and integrated multilevel studies.

Reference: Rovetta, Bortolotti, and Di Berardino (2026), *When humans and agents form a collective*, https://doi.org/10.3389/forgp.2026.1941058

## 2. What SympoeticBench should measure

### 2.1 Configuration integrity

At every cycle, pin:

- Pseudonymous team and principal IDs.
- Participant type (human or agent), role, and authority-policy digest.
- Model snapshot and relevant adapter revision for every agent.
- Memory policy and participant consent scope.
- Task, scenario, tool catalogue, and environment digests.
- Team state before and after the cycle.

A role name is not an authority grant. A principal does not inherit another principal's permissions when membership or role assignments change.

### 2.2 Collective functioning

Measure enacted evidence of:

- Role clarity and role reconfiguration.
- Distribution and retrieval of expertise.
- Shared-plan creation, correction, and persistence.
- Handoff fidelity and repair.
- Evidence and uncertainty preservation.
- Conflict detection and decision rights.
- Duplicate work, coordination burden, and idle capacity.
- Human control and contestability.
- Memory reuse, expiry, correction, and withdrawal.

These are observable team processes. They do not, by themselves, establish collective intelligence.

### 2.3 Collective intelligence

Only investigate this after measures and team boundaries are qualified. A valid collective-intelligence claim needs a prespecified task universe with multiple diverse tasks, defensibly comparable outcome measures, sufficient team observations, and evidence that performance generalizes beyond a single task or episode.

Do not calculate an omnibus score from a small collection of unrelated task outcomes and call it CI. Establish the measurement model, reliability, task sampling, and cross-condition comparability first. Report task-level results and uncertainty before any latent or aggregate team-capacity estimate.

## 3. Cycle receipt protocol

The Rust trajectory model stores a team identifier and an ordered series of cycle receipts. Every cycle records:

- A contiguous zero-based cycle index and unique run ID.
- Scenario ID and task outcome digest.
- Team-state digest before and after the cycle.
- Artifact digest.
- Current participant roster, roles, authority digests, memory consent, and model snapshots.
- Explicit change events for membership, roles, authority, memory policy, per-member memory consent, and model snapshot.
- The digest of the preceding cycle receipt.
- A canonical digest of the cycle receipt itself.

The next cycle must reference the preceding cycle digest and use the preceding cycle's state-after digest as its state-before digest. This creates a verifiable continuity chain. It does not prove that the state itself is truthful; the state and artifact digests must be generated by the trusted harness and backed by inspectable evidence.

### 3.1 Change events are not optional metadata

If a principal is added or removed, record it. If a role or authority digest changes, record it. If memory policy or a member's consent changes, record it. A principal's participant type cannot silently change; use a new principal ID.

A change event must correspond to an actual before/after configuration difference. The validator rejects both unlogged changes and invented change events.

### 3.2 Persistent memory and consent

For `team_opt_in_persistent` memory, every current member must have `explicit_opt_in` and the cycle must carry a consent digest. A member who has not opted in cannot be included in the persistent-memory scope merely because another team member has consented.

A membership change, memory-policy change, or consent change must be explicit. Revocation and deletion semantics must be handled by the real storage/retention system; this receipt format does not claim that a digest proves data deletion.

## 4. Experimental design

Start with a development and pilot sequence rather than a global team leaderboard.

For each persistent-team task family:

1. Run a baseline cycle with a frozen team configuration.
2. Run repeated cycles on comparable but non-identical tasks.
3. Inject controlled events: a role change, a specialist becoming unavailable, a new member, a changed authority policy, a corrected source, a memory-policy change, and a consent revocation.
4. Test whether shared plans and justified knowledge persist while stale or revoked information is not reused.
5. Run held-out tasks that require transfer rather than repetition of a memorized plan.
6. Compare persistent teams with reset-per-task teams under matched information, time, model, and tool budgets.

Where feasible, include human-only teams, AI-only teams, reciprocal human-AI teams, and conventional assistant baselines. Counterbalance membership and role order.

## 5. Measures and failure modes

Report separate metrics for:

- Task success and domain quality.
- Collaboration gap and synergy against matched solo baselines.
- Causal contribution and handoff recovery.
- Shared-plan retention and correction latency.
- Role-confusion and unauthorized authority inheritance.
- Knowledge/provenance retention and stale-evidence reuse.
- Member onboarding and departure recovery.
- Human agency, workload, and independent capability gain.
- Memory-consent violations and withdrawal propagation.
- Cost, latency, tool calls, and coordination overhead.

Failure injection should include stale shared plans, conflicting versions, duplicated specialists, missing team members, authority changes, memory contamination, false consensus, and an unknown tool outcome at a cycle boundary.

## 6. Competitive positioning

- **AgentWorld (2026):** 100 human-annotated tasks plus 100 augmented variants, 3–20 agents, and 50+ rounds. Its Causal Collaboration Effectiveness (CCE) measures graph-based contribution to outcomes. SympoeticBench should borrow the lesson that activity volume is not contribution, but extend the evaluation to human agency, consent, provenance, learning, and persistent organizational continuity. https://arxiv.org/abs/2609.31590
- **The Collaboration Gap (COLM 2026):** matched solo/pair performance and relay-order sensitivity expose collaboration degradation that single-agent capability rankings miss. https://www.microsoft.com/en-us/research/publication/the-collaboration-gap/
- **AOBench v0.4.1:** a role-aware operational benchmark with 88 tasks and 29 environments. It is an external operational baseline, not a substitute for persistent human-AI team research. Its own benchmark card warns against production-safety claims from frozen mock environments. https://mskazemi.com/aobench/latest/about/benchmark-card/

## 7. Provisional milestones

| Stage | Evidence required | Permitted claim |
|---|---|---|
| M0 — Receipt integrity | Schema, cycle digest, state-chain and roster-change tests | The trajectory record is structurally valid |
| M1 — Process qualification | Blinded annotations for roles, handoffs, plan state, consent and provenance | Selected collective-functioning measures are reproducible |
| M2 — Local relations | Matched tests of configuration changes and team processes | Bounded relationships for tested task families |
| M3 — Longitudinal team study | Repeated cycles, attrition/turnover, comparable outcomes, held-out tasks | Team-level development or deterioration for the tested configuration |
| M4 — Collective intelligence | Qualified multi-task measurement model, adequate sampling, cross-task generalization and independent replication | A bounded collective-intelligence claim for the stated task universe |

No stage is passed by merely increasing the number of sessions. Configuration, measurement validity, team continuity, and inference boundaries must be demonstrated.

## 8. Implementation boundary

The Rust implementation in `crates/domains/sympoetic-bench/src/trajectory.rs` validates receipt chains and the consistency of explicit team changes. The CLI command is:

```bash
cargo run -p sympoetic-bench -- validate-trajectory \
  --input path/to/team-trajectory.json
```

The validator is not a team orchestrator, memory store, consent-management system, or empirical CI estimator. The current implementation verifies recorded continuity claims and configuration-change receipts; a trusted harness must produce the underlying evidence.

## 9. Non-claims

A valid trajectory is not proof of a mind, shared subjective experience, sentience, a literal group mind, or collective intelligence. The benchmark measures observable configurations, interactions, outcomes, and multi-cycle performance. Collective-intelligence claims require a separate validated research programme.
