# Electric Thermal Loss Ledger Oracle

A dependency-free Rust reference for two related but deliberately separate ledgers:

1. Electrical load accounting at declared meter boundaries.
2. Evidence-backed allocation of declared component losses into thermal nodes.

This crate does not solve temperatures, heat transfer, coolant flow, thermal networks, battery electrochemistry or aircraft mission feasibility. It is an accounting and provenance reference that the existing thermal-network and mission-solver owners may consume.

## Electrical load ledger

Each electrical load has a unique load ID, a unique meter-boundary ID, a category, a non-negative finite power reading and an evidence-manifest digest.

Categories:
- propulsion DC input measured at inverter DC terminals;
- thermal-management electrical load;
- other auxiliary electrical load;
- upstream distribution loss, where not already included in the downstream load readings;
- battery-terminal total, when only the battery-terminal meter reading is available.

A battery-terminal-total reading is exclusive: it cannot be added to any downstream branch loads. This prevents summing the battery total and its own consumers twice. When branch readings are used, each physical meter boundary must occur once. Total terminal power and energy are the sum of the supplied non-overlapping readings. Category subtotals are optional: a category with no meter is unknown, not zero. When only a battery-terminal-total meter is supplied, all branch category subtotals are unknown.

Thermal-management electrical consumption remains a separate mission load. It is not automatically emitted as battery heat or component heat.

## Thermal loss allocation ledger

Each declared loss source has a unique source ID, component ID, loss class, non-negative finite loss power, evidence-manifest digest and zero or more allocations to thermal node IDs.

For each source, supplied allocation fractions must be finite and in [0, 1], with unique node IDs and a sum no greater than 1.0. The report calculates:

- allocated heat = loss power × sum(allocation fractions);
- unallocated loss = loss power × (1 - sum(allocation fractions));
- allocation residual = declared loss - allocated heat - unallocated loss.

A source with no allocations has 100% unallocated loss. This closes the source-accounting identity without inventing a thermal node. It remains incomplete thermal evidence until the allocation is supported.

Multiple sources may contribute to one thermal node. Reports retain each source identity and produce deterministic node totals.

## No double counting

A conversion loss in the motor/inverter/transmission chain is already included in the upstream electrical demand required to deliver useful shaft power. Allocating that loss into thermal nodes does not add it again to electrical demand.

Similarly, a pump/fan/compressor electrical load is not automatically heat generated in the battery. Any heat generated by TMS equipment must be represented by a separately identified physical loss source and explicit node allocation.

An electrical load ledger and a thermal loss allocation ledger may reference related evidence, but neither is added into the other.

## Verification

```bash
cargo fmt --manifest-path tools/electric-thermal-loss-ledger-oracle/Cargo.toml -- --check
cargo test --locked --manifest-path tools/electric-thermal-loss-ledger-oracle/Cargo.toml
cargo clippy --locked --manifest-path tools/electric-thermal-loss-ledger-oracle/Cargo.toml --all-targets -- -D warnings
```

All included fixtures are synthetic. A passing ledger test proves only the declared accounting and identity semantics. It does not validate physical heat partition, component temperatures, cooling performance, battery safety, aircraft mission feasibility or airworthiness.


## Unknown versus measured zero (v0.2)

The electrical report carries an explicit metering mode. When only a battery-terminal-total reading exists, propulsion/TMS/auxiliary/distribution subtotals are `None`, not zero. In branch mode, a category with no supplied meter is also `None`; a physical zero is only reported as `Some(0.0)` when an identified meter explicitly reports zero. This prevents missing submeter evidence from being misrepresented as zero consumption.
