# symthaea-audit

A standalone, LLM-agent-driven architecture and trust auditor. Points a tool-calling
agent at a repository (or a named subsystem within one), lets it explore read-only, and
produces a structured six-section report — with every claim required to carry a
`file:line` citation.

Deliberately independent of `symthaea-core` and the main `symthaea` crate: no HDC, no
Phi, no consciousness engine. It compiles fast and runs anywhere. This is a tool, not a
demonstration of Symthaea's own cognition — see [`llm_client.rs`](src/llm_client.rs) for
the one place that trades code reuse for that independence.

## Why this exists

An AI system that can find and explain its own gaps is more trustworthy than one that
only ever describes its own strengths. This tool is a narrow, concrete instance of that
idea: point it at any repo (including this one — see [Self-audit results](#self-audit-results)
below) and it tells you what's actually wired, what's claimed but dark, what's
safety-critical and untested, what should be deleted, and what should be gated before
release.

## Quick start

```bash
cargo build -p symthaea-audit --release
./target/release/symthaea-audit /path/to/some/repo
```

By default it auto-detects an LLM backend from your environment (see
[Backends](#backends) below) and writes a timestamped report to the current directory —
never into the audited repo, so repeated runs never mutate the target or silently
overwrite a prior report.

## The report

Every run produces exactly six sections, each claim required to cite `file:line`:

1. **WIRED** — what's actually connected end-to-end in the real code path
2. **CLAIMED BUT DARK** — documented/implemented things never invoked from production
   wiring, or documentation that overclaims relative to the code (and, just as
   important, places where the docs are *already* appropriately honest — the model is
   told not to manufacture severity where none exists)
3. **SAFETY-CRITICAL** — what gates irreversible, dangerous, or high-stakes behavior
4. **UNTESTED** — safety-relevant code paths with no test coverage
5. **SHOULD DELETE** — dead, orphaned, or superseded code
6. **SHOULD GATE** — what would need a release threshold before shipping

Every report ends with a fixed disclaimer: it was generated by an LLM agent from
repository content it doesn't control, so its citations should be checked before being
treated as ground truth for a release decision. Sandboxing stops filesystem escape;
nothing stops a hostile target repo's own content from trying to steer the model's
conclusions. That's a real, open limitation, not something this tool claims to solve.

## Flags

| Flag | Default | What it does |
|---|---|---|
| `<target>` (positional) | — | Path to the repo/directory to audit |
| `--focus <text>` | whole repo | Scope the audit to a named subsystem, e.g. `--focus "the Phi subsystem in src/cognitive_loop/"` |
| `--out <path>` | `./symthaea-audit-report-<name>-<timestamp>.md` | Where to write the report |
| `--llm-provider {auto,ollama,anthropic,openai}` | `auto` | Backend selection; `auto` reads env vars (see below) |
| `--model <name>` | backend-specific | Override the model name |
| `--ollama-base-url <url>` | `http://localhost:11434` | Ollama endpoint override |
| `--openai-base-url <url>` | `https://api.openai.com/v1` | OpenAI-*compatible* endpoint override — this is how you point it at OpenRouter, vLLM, etc. |
| `--max-turns <n>` | `40` | Turn budget before returning a truncated partial report |
| `--allow-exec <cmds>` | *(disabled)* | Comma-separated exact commands the model may run via `run_check` (e.g. `"cargo check"`). Empty means `run_check` isn't even advertised to the model — see [Safety model](#safety-model) |
| `--single-shot-paths <paths>` | *(off)* | Comma-separated files/dirs read wholesale into the first turn, instead of making the model plan multi-turn exploration. Tool access stays on. Aimed at smaller/local models — see [Working with weak/free models](#working-with-weakfree-models) |
| `--verify` | `false` | Run a second pass that re-checks each cited claim, appending (never replacing) a Verification Notes section marking each VERIFIED / UNVERIFIED / CONTRADICTED |
| `--no-hints` | `false` (hints on) | Disable the free, deterministic pre-scan — see below |
| `--review-diff <range>` | *(off)* | Review a diff instead of auditing the whole repo — see [Diff review mode](#diff-review-mode) |

## Diff review mode

The "trusted repo companion" idea: the same auditor machinery, run continuously on
diffs instead of once on a whole repo.

```bash
symthaea-audit /path/to/repo --review-diff "main..HEAD"
symthaea-audit /path/to/repo --review-diff "HEAD~3..HEAD" --focus "fixes the login timeout bug"
```

`--review-diff` takes any git ref range. It replaces the six-section whole-repo report
with a five-section diff report, and the model still has full read-only tool access to
the repo's *current* state (not just the diff text) — so it can check whether a changed
function has a test file even if this diff didn't touch one, or grep for other places a
changed behavior is described:

1. **SCOPE** — does the diff do one coherent thing, or touch files that don't obviously
   relate to its stated purpose (`--focus`, if given)?
2. **SAFETY-CRITICAL SURFACE** — does it touch code gating irreversible/dangerous/
   high-stakes behavior?
3. **TEST COVERAGE OF THE CHANGE** — does each non-trivial logic change have a
   corresponding test change?
4. **DOCS VS. THE NEW REALITY** — does the diff change behavior an existing comment or
   README describes, without updating it?
5. **RELEASE GATE** — the single most important concrete condition before merging.

`--verify` and the pre-scan hints both still apply in this mode. Pre-scan hints are
whole-repo, not diff-scoped, so treat them as background context rather than findings
about the diff itself.

**Known limitation, observed directly, not theoretical**: reviewing this crate's own
`70fcd49066` commit (adding telemetry fields to the exact `SpectralMIPFinder` struct
this README describes as gating robot motor safety) with `qwen2.5-coder:7b`, the model
correctly summarized SCOPE, TESTS, and DOCS, but answered SAFETY-CRITICAL SURFACE with
"no safety-critical code is touched" — despite `--focus` explicitly naming
`SpectralMIPFinder`. Same model-capability gap documented in
[Working with weak/free models](#working-with-weakfree-models) below, now confirmed in
this mode too: the mechanism (citations, schema, tool use) works; connecting "this
struct's name" to "this struct's actual role" is where a small model falls short. Don't
trust SAFETY-CRITICAL SURFACE answers from a weak model without reading the diff
yourself.

## Backends

Three backends, all going through one minimal blocking `complete(system, history)`
trait (`src/llm_client.rs`) built on `ureq`, not `reqwest`/tokio:

- **Ollama** (default fallback, no API key) — `http://localhost:11434` unless overridden
- **Anthropic** — reads `ANTHROPIC_API_KEY` (and optionally `ANTHROPIC_MODEL`,
  `ANTHROPIC_BASE_URL`)
- **OpenAI-compatible** — reads `OPENAI_API_KEY` (and optionally `OPENAI_MODEL`,
  `OPENAI_BASE_URL`); works against any OpenAI-shaped endpoint, e.g. OpenRouter via
  `--openai-base-url https://openrouter.ai/api/v1`

`auto` picks, in order: explicit `--llm-provider` flag, `SYMTHAEA_AUDIT_LLM_PROVIDER`
env var, `ANTHROPIC_API_KEY` present, `OPENAI_API_KEY` present, then Ollama.

This module is a **deliberate exception** to "don't duplicate implementations" — the
main `symthaea` crate already has a fuller `LLMBackend` trait with the same three
providers, but importing it would pull in the whole consciousness stack this crate
exists to avoid. See the module doc for the full reasoning and the acknowledged
maintenance cost (the two implementations can drift if a provider's API shape changes).

## Safety model

This tool audits arbitrary, potentially untrusted repositories, so the sandbox boundary
is the one piece of genuinely safety-critical logic here:

- **No write access at all.** There is no `write_file` tool. This is a read-only
  auditor by design.
- **Every path argument is canonicalized and checked against the target root**
  (`resolve_in_sandbox` in `src/tools.rs`), rejecting `..`/absolute/symlink escapes —
  including symlinks encountered *during* a recursive directory walk, not just at the
  top-level request.
- **`run_check` is off by default and allow-listed, not free-form.** With no
  `--allow-exec`, the tool isn't even told `run_check` exists — a prompt-injected
  instruction in the audited repo's own content can't make it try. When enabled, only
  the exact whitelisted command strings run, via `Command::new(program).args(args)`
  (never a shell), so there's no injection surface even within the whitelist.
- **`git`/`grep` subcommands use discrete args, never shell-string concatenation.**

None of this defends against the model's *conclusions* being steered by hostile content
in the target repo — see the disclaimer footer above.

## Free, zero-cost pre-scan (on by default)

Before any LLM call, a deterministic Rust-only pass (`src/heuristics.rs`) scans the
target for two patterns and feeds them into the model's first turn as unverified hints:

1. **A function called with `None` in one place, non-`None` at the same argument
   position elsewhere** — resolves both literal `None` and the `let x = None;`
   local-binding pattern real code actually uses. Groups by `(callee, arity)` and
   excludes common generic wrapper types (`Mutex`, `Arc`, `Vec`, ...) to avoid drowning
   in coincidental name collisions.
2. **`pub fn`s defined outside test code with no usage found anywhere except (at most)
   tests** — usage counted via bare identifier-token frequency, so `.method()`,
   `Type::method()`, and bare `function()` calls are all covered. Deliberately biased
   toward under- rather than over-reporting (a same-named item anywhere hides real dead
   code under that name). Excludes operator/macro-dispatched trait methods (`fmt`, `eq`,
   `cmp`, `index`, `deref`, ...) and vendored/benchmark/example/patch paths, where
   "only called from its own test" is the structurally correct shape, not a finding.

Both detectors strip comments and string literals first (nesting-aware block comments,
regular and raw strings), replacing them with equal-length whitespace so line numbers
stay correct — otherwise example call syntax in a doc comment or test fixture gets
scanned as if it were live code.

## Working with weak/free models

Small/local models are much better at reading a lot of text in one pass than at
planning a multi-turn exploration strategy. If you're not paying for a frontier model,
combine `--single-shot-paths` (pre-load the relevant files) with the pre-scan hints
(on by default) to give the model as little planning to do as possible. `--verify` can
also help even with a weak model, since re-checking one specific cited claim is a much
easier task than producing the original analysis.

## Self-audit results

This tool has been run against the `symthaea` monorepo itself (a real, ~1.68M-line, 7,178
`.rs`-file repo) as part of its own development. It independently found, and a human
confirmed by hand:

- The exact production-vs-test `None`/`Some` mismatch pattern that was this session's
  flagship manual finding (`ConsciousnessEngine::new`)
- A real, previously-undocumented broken build under a non-default feature flag
  (`cargo check -p symthaea-broca --features mamba-cpu` → 29 errors)
- A live safety-critical mechanism (`SpectralMIPFinder::adapt()`, which runs every 94
  cycles in production gating robot motor safety) whose state was never observable —
  since fixed
- A genuinely orphaned duplicate implementation (`compute_true_phi_parallel`) sitting
  alongside the actual load-bearing exhaustive-Φ reference used elsewhere

None of these were fabricated or exaggerated to make the tool look good — each was
independently verified by direct inspection before being acted on or logged. See
`SYMTHAEA_IMPROVEMENT_PLAN_2026-07.md` at the monorepo root for the full record.
