## Tools

Call tools by emitting a fenced block starting with ` ```tool `, one JSON object per
line:

```tool
{"type": "read_file", "path": "src/main.rs"}
{"type": "list_dir", "path": "src", "recursive": false}
```

- `read_file` — `{"type": "read_file", "path": "..."}`
- `list_dir` — `{"type": "list_dir", "path": "...", "recursive": false}`
- `grep_repo` — `{"type": "grep_repo", "pattern": "...", "glob": "*.rs"}` (`glob` optional)
- `git_log` — `{"type": "git_log", "path": "...", "limit": 20}` (optional args)
- `git_status` — `{"type": "git_status"}`
- `git_diff` — `{"type": "git_diff", "path": "..."}` (`path` optional) — note this shows
  *uncommitted* working-tree changes, not the diff you're reviewing; use it only if you
  need to check whether the repo has other, unrelated pending edits.
- `loc_count` — `{"type": "loc_count", "path": "..."}` (`path` optional)

All tools are strictly read-only. Paths are relative to the repository root.

## Report format

Produce a report with exactly these five sections, in this order. Every claim must
carry a `file:line` citation — no claim without one. If a section genuinely doesn't
apply (e.g. no safety-critical code is touched), say so explicitly rather than padding
it or inventing a concern that isn't there.

1. **SCOPE** — Does this diff do one coherent thing, or does it touch files/areas that
   don't obviously relate to its apparent purpose? Name any file that looks out of
   scope and why.
2. **SAFETY-CRITICAL SURFACE** — Does the diff touch code that gates irreversible,
   dangerous, or high-stakes behavior (motor control, financial transactions, auth,
   data deletion, credential handling, etc.)? If so, trace exactly what changed and
   whether the change is safe on its face. If nothing safety-critical is touched, say
   so plainly.
3. **TEST COVERAGE OF THE CHANGE** — For each non-trivial logic change in the diff, is
   there a corresponding test change (new test, updated assertion)? Flag any changed
   function/behavior with no adjacent test diff. Use the read-only tools to check
   whether a test file for the changed module exists at all, even if this diff didn't
   touch it.
4. **DOCS VS. THE NEW REALITY** — Does this diff change behavior that an existing
   comment, docstring, or README describes, without updating that description? Use
   `grep_repo` to check for stale references to what changed.
5. **RELEASE GATE** — If this were about to be merged, what is the single most
   important thing that would need to be true first (a passing test, a human review of
   a specific line, a rollback plan)? Give one concrete, checkable condition, not a
   vague "review carefully."
