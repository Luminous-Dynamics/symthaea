# SFEB MON-005 — Witnessed Evidence Checkpoints

## Status

Executable reference model; locally run with Node.js v22.16.0. **39/39 deterministic cases pass.** The tests also verify **496 Merkle inclusion proofs** across every leaf position in tree sizes 1 through 31.

This is an assurance-model prototype, not a production transparency service. The witness identities and their state are simulated inside one process.

## What it implements

- Tenant-scoped evidence records with a domain-separated SHA-256 record chain.
- A Merkle Tree Hash following the RFC 9162 tree shape and distinct `0x00` leaf / `0x01` node prefixes.
- Inclusion-proof generation and verification.
- Ed25519 signatures over tenant-bound checkpoints.
- A 3-of-4 witness quorum and a witness-set identifier pinned in the checkpoint.
- Fresh auditor challenge nonces, idempotent retry of the exact same checkpoint signature, and rejection of a different checkpoint reusing the same challenge.
- Monotonic checkpoint epochs and previous-checkpoint linkage.
- Full prior-prefix recomputation by each witness before it signs a later checkpoint. This rejects a database operator who rewrites historical events and recomputes the local hash chain.
- Negative controls for tampering, reordered or substituted records, cross-tenant substitution, insufficient quorum, duplicate signers, unknown signers, checkpoint mutation, replay, epoch rollback/gaps, forks, and historical-prefix rewrites.

A checkpoint commits to an evidence record that includes source, authority, execution and outcome-readback digest fields. In this test fixture those values are placeholders generated by the test. The prototype does not authenticate the real upstream receipts or prove that the external sink enforced the authority fence.

## Why 3-of-4

A 3-of-4 quorum has an intersection of at least two witnesses with every other 3-of-4 quorum. Under the stated assumption that no more than one witness is Byzantine, at least one intersecting witness is honest and durably refuses to sign two different checkpoint heads for the same tenant/epoch. Three signatures also remain available when one witness is offline.

This safety argument is conditional. It requires each witness to:

1. Fetch and independently verify the evidence log, rather than trust a root supplied by the operator.
2. Persist its latest accepted (tenant, epoch, checkpoint_hash, tree_size, root) in a separate trust domain.
3. Enforce one checkpoint hash per (tenant, epoch) with an atomic durable compare-and-set / uniqueness constraint.
4. Return the same stored signature for an exact retry, and reject a conflicting candidate.
5. Keep its private key separate from the log operator and the other witness operators.

The in-memory class in this prototype does not qualify any of those operational requirements.

## Known limits

- Witness state is in-memory; a process restart loses rollback protection.
- Four witnesses are simulated in a single process; this is not operational independence or a distributed Byzantine-fault-tolerance result.
- Deterministic Ed25519 fixture keys are test-only and must never be deployed.
- Canonicalization is a strict local JSON subset, **not a complete RFC 8785 JCS implementation**. Production must use a conformant, cross-language JCS implementation and test its published vectors.
- Each checkpoint recomputes the complete prior prefix. This is deliberately simple for the prototype; scale with RFC 9162 consistency proofs or an independently operated transparency-log service.
- No PostgreSQL witness store, network protocol, HOM/KMS Integration, key rotation/revocation, trusted timestamp authority, external sink, or live source connector exists here.
- A valid signature proves that a trusted key signed a checkpoint; it does not prove that the underlying receipt is truthful. Source, authority, execution and postcondition evidence must be independently validated at their own boundaries.

## Next qualification gate

Implement four independent witness services with durable monotonic state, 3-of-4 quorum, a per-tenant/per-epoch uniqueness constraint, restart/replay tests, conflicting-head race tests, key rotation and revocation, and a real RFC 9162 consistency-proof implementation. Then anchor SFEB checkpoint digests in an established log (e.g. Sigstore Rekor/Tessera or a Certificate Transparency-compatible service) rather than claiming that this prototype replaces a mature transparency ecosystem.
